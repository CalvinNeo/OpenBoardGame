# 《拼布艺术》(Patchwork) 完整基础规则与电子版开发设计文档

这份文档将面向玩家的**基础规则**与面向开发者的**程序逻辑**进行了全面整合。你可以将此作为完整的 Game Design Document (GDD) 来指导电子版的开发。

---

## 第一部分：游戏基础规则 (面向玩家)

### 1. 游戏概述与目标
《拼布艺术》是一款支持双人的策略博弈桌游。两位玩家扮演织布工，需要在有限的时间内，使用“按钮”（货币）购买各种形状的“布块”，并将其缝合在自己的 9x9 拼布板上。
* **游戏目标**：在游戏结束时获得最高的分数。
* **计分核心**：游戏结束时，你手中剩余的每一个“按钮”算作 1 分，但拼布板上每一个**未被填满的空格**将扣除 2 分。

### 2. 核心机制：双重资源与动态回合
* **双重资源**：游戏中有两种主要资源——**按钮**（金钱/分数）和**时间**。购买布块不仅需要支付按钮，还需要消耗时间（在时间板上前进相应步数）。
* **动态回合（追赶机制）**：游戏**没有固定的交替回合**。行动权始终属于在时间板上**位置落后**（离终点较远）的玩家。如果一名玩家行动后依然落后，他将继续行动。

### 3. 玩家的两个可选行动
轮到你时，你必须且只能从以下两个行动中选择一个：
* **行动 A：推进并拿取按钮**
  将你的时间标记直接移动到对手时间标记的**正前方一格**。你移动了多少格，就从银行拿取多少个按钮。
* **行动 B：购买并放置布块**
  1. 查看公共圆阵中“中立标记”**顺时针方向的前三个**布块。
  2. 选择其中一个，支付其标示的“按钮成本”。
  3. 将中立标记移动到你买走的布块原来的位置。
  4. 将布块放置在你的 9x9 拼布板上（可随意旋转、翻转，但不能重叠或越界）。
  5. 根据布块上标示的“时间成本”，将你的时间标记在时间板上向前移动相应的步数。

### 4. 时间板上的奖励
在时间板上移动时（无论是通过行动 A 还是行动 B）：
* **跨越按钮图标**：每当你经过或停在时间板上的“按钮图标”时，计算你拼布板上所有布块自带的蓝色按钮图标总数，从银行拿取等量的按钮作为“收入”。
* **跨越皮革补丁**：时间板上有 5 个单格（1x1）的皮革补丁。谁**第一个**经过或停在它上面，谁就立刻获得它，并必须马上拼入自己的拼布板。

### 5. 特殊奖励：7x7 完美拼布
第一位在自己的拼布板上填满任意一个 7x7 区域（没有任何空隙）的玩家，立即获得“特殊奖励板块”（价值 7 分）。

## 第二部分：电子版开发核心逻辑 (面向开发者)

### 1. 核心数据结构与游戏状态 (State Representation)

* **Game State**:
    * `turn_player`: `0` (Player A) 或 `1` (Player B)。
    * `neutral_token_index`: 整型，指向当前圆阵中中立标记所在的布块索引。
    * `special_tile_available`: 布尔值，7x7奖励板块是否已被领取（初始为 `true`）。
* **Player State** (每位玩家独立维护):
    * `buttons`: 整型，当前拥有的按钮数量（初始 `5`）。
    * `time_position`: 整型，范围 `0` 到 `53`（终点），表示在时间板上的绝对位置。
    * `quilt_board`: `9x9` 的二维数组（`0` 表示空，`1` 表示已被填充）。
    * `button_income`: 整型，当前拼布板上每回合可触发的按钮收益总数。
    * `has_special_tile`: 布尔值，是否获得7x7奖励。
* **Patch Data Structure** (布块对象):
    * `id`: 唯一标识符。
    * `shape`: 二维数组或相对坐标列表，用于碰撞检测、旋转和翻转。
    * `cost_buttons`: 整型，购买花费。
    * `cost_time`: 整型，推进时间。
    * `income_buttons`: 整型，附带的按钮图标数。

### 2. 详细初始化逻辑 (Setup Phase)
1.  **玩家数据**：初始化双人数据，`buttons = 5`，`time_position = 0`，清空 `quilt_board`。
2.  **布块圆阵**：
    * 将 33 个常规布块实例化并随机打乱，存入一个环形数组 `patch_circle`。
    * **寻找起点**：遍历数组，找到面积最小（1x2，耗费 2 按钮 1 时间）的布块。将 `neutral_token_index` 设置为该布块的**顺时针下一位**（即 `(index + 1) % 33`）。

### 3. 回合判定逻辑 (Turn Priority Flow)
* **当前玩家判定算法**：
    * 比较两人的 `time_position`。值较小的一方为当前行动玩家。
    * **关键边界条件 (叠放规则)**：如果 `PlayerA.time_position == PlayerB.time_position`，则**后到达该位置的玩家**（物理上叠在上方）被视为“落后”，拥有行动权。

### 4. 玩家行动校验与流转 (Actions & Validations)

#### 行动 A：推进并获取按钮
* **逻辑计算**：
    1.  目标位置：`target_pos = Opponent.time_position + 1`。若 `target_pos > 53`，则限制为 `53`。
    2.  获得按钮数：`gained_buttons = target_pos - CurrentPlayer.time_position`。
    3.  更新状态：`CurrentPlayer.buttons += gained_buttons`。
    4.  移动标记并触发沿途事件（见第 5 节）。

#### 行动 B：购买并放置布块
* **前提校验**：
    1.  从 `neutral_token_index` 开始，向后获取 3 个未被购买的布块。
    2.  校验资金：`CurrentPlayer.buttons >= Patch.cost_buttons`。
* **操作流转**：
    1.  **扣除资源与更新圆阵**：扣除按钮。将 `neutral_token_index` 移至该布块位置，将其从可选池中标记为移除。
    2.  **几何变换与碰撞检测**：允许布块 90°/180°/270° 旋转或水平/垂直翻转。校验布块的 `1` 部分不可超出 `9x9` 边界，且不能与 `quilt_board` 中已有的 `1` 重叠。
    3.  **写入数据**：确认放置后，更新 `quilt_board` 及 `CurrentPlayer.button_income += Patch.income_buttons`。
    4.  **检查 7x7**：运行 7x7 检测算法。
    5.  **移动时间**：根据 `Patch.cost_time` 移动时间标记，并触发沿途事件。

### 5. 时间轴触发事件与结算顺序 (Board Events)
移动 `time_position` 时，需遍历起点到终点之间的所有索引（左开右闭区间）：
1.  **经过按钮收入 (Button Income)**：若经过对应索引，立刻给予玩家 `CurrentPlayer.button_income` 数量的按钮。
2.  **经过皮革补丁 (Special Patch)**：若经过且补丁未被拿走，**立即中断移动**。玩家必须强制放置这个 1x1 的补丁到拼布板上（同样执行碰撞与7x7检测）。放置后，继续完成剩余的移动结算。

### 6. 7x7 奖励判定算法 (7x7 Check)
* **遍历逻辑**：在 `9x9` 矩阵中，以 `(0,0)` 到 `(2,2)` 为左上角顶点，共计 9 个可能的 `7x7` 区域。
* **检测**：检查这 9 个区域中是否有一个区域内的 49 个格子全部为 `1`。如果成立且 `special_tile_available == true`，则玩家获得该奖励并更新全局状态。

### 7. 终局判断与计分公式 (Endgame)
* **结束条件**：两名玩家的 `time_position` 均到达 `53`。
* **最终计分公式** (严格按照此公式核算)：

$$Final Score = Total Buttons + Special Tile Bonus(7) - (Empty Spaces \times 2)$$

* **平局判定 (Tie Breaker)**：若总分相同，先到达终点格（53）的玩家获胜。

## 第三部分：无法获取/需额外定义的硬编码资源

由于缺乏官方实体版的数据字典，开发此电子版你需要自行录入或构建以下核心资源：

1. **33 个常规布块数据表 (Patch Dictionary)**：
   需要精准录入每个布块的：形态矩阵（或相对坐标）、按钮成本、时间成本、自带按钮收入数量。
2. **时间板轨道定义 (Track Layout)**：
   一个长度为 54（0-53）的数组，需明确标注：
   * 哪些索引位置是“按钮收入”触发点（通常有 9 个）。
   * 哪些索引位置是“皮革补丁”放置点（共 5 个）。
3. **美术资源 (Assets)**：
   布块的纹理贴图、拼布板背景、UI 交互按钮（旋转/翻转图标）等。


# QA
## 问题和回答1
### 1. `patch_circle` 被买走的布块：移除还是保留空位？
**建议：直接从数组中移除并收缩。**
* **原版物理逻辑**：物理桌游中，中立标记会“占据”被买走布块留下的空位，玩家看接下来的 3 个布块时，会自动跳过这个标记。
* **电子版最优解**：如果你在数组中保留 `null` 或空位，每次获取“前三个”时都需要写额外的 `while` 循环去跳过空位，这会增加算法复杂度且容易出 Bug。最优雅的做法是使用动态数组（或环形链表），买走后直接 `remove(index)`。中立标记直接指向原本的下一个元素。这样，获取接下来的 3 个选项只需简单的 `(index + 0), (index + 1), (index + 2)` 再对当前数组长度取模即可。

### 2. 行动 A：追赶到终点（53）的计算
**逻辑完全正确。**
* 终点格是绝对的物理边界（不会出现 54）。
* 如果对手已经在 53（终点），你执行行动 A 时，理论目标是 `53 + 1`，但必须做截断（Clamp）处理，强制设定 `target_pos = 53`。
* 你获得的按钮数量严格等于实际移动的格数，即 `53 - CurrentPlayer.time_position`。

### 3. 一次移动跨过多个皮革补丁？
* **原版事实**：在原版《拼布艺术》的硬编码数据中，皮革补丁之间的距离通常大于 6 格，而所有布块的最大时间成本通常不超过 6。因此在正常游戏中，**不可能**一次移动跨越多个皮革补丁。
* **代码鲁棒性（Robustness）设计**：为了防止未来添加自定义布块（Mod）导致 Bug，你的状态机应当支持依次结算。即：经过第一个补丁 -> 暂停移动 -> 等待玩家放置并校验 -> 继续完成剩余的 `time_cost` 移动 -> 遇到第二个再暂停。

### 4. 一次移动跨过多个按钮图标（收入）？
* **原版事实**：同样，原版按钮图标的间距设计也保证了玩家不可能一次跨越两个收入线。
* **代码鲁棒性设计**：**是的，应该多次触发**。算法在遍历 `start_pos` 到 `end_pos` 的路径时，如果索引数组命中两次 Button Income 标记，就应该执行两次 `CurrentPlayer.buttons += button_income`。

### 5. 轨道格同时是“按钮图标”和“皮革补丁”的结算顺序
* **原版事实**：原版地图中这两者绝对不会重叠在同一格。
* **代码鲁棒性设计**：如果出现这种自定义极端情况，建议的程序结算顺序是：**先结算按钮收入，再结算皮革补丁**。
* **原因**：按钮收入是静默的底层数据修改（数值相加），瞬间即可完成；而获取皮革补丁会中断当前的游戏流，呼出 UI 强制要求玩家进行放置（涉及拖拽、旋转、碰撞检测等异步交互）。先处理完底层数值，再处理复杂的异步交互，能让你的状态机更稳定，不易产生脏数据。

### 6. 平局判定的“先到达 53”
**理解完全准确。直接追到 53 的玩家算“后到达”。**
* **物理桌游规则**：当两个时间标记在同一个格子上时，后来的标记必须叠在先来的标记上面。上面的人算“落后”，底下的人算“领先”。
* **程序逻辑**：如果 A 已经在 53，B 执行行动 A 追到了 53，此时 A 依然是“先到达者”。
* **实现建议**：不需要记录复杂的时间戳，只需要给每个玩家对象增加一个布尔值 `is_first_to_finish = false`。在 `time_position` 更新的函数中加个拦截：当任意玩家的 `time_position` 首次达到 53 时，检查对手是否已到 53。如果对手没到，就把自己的 `is_first_to_finish` 设为 `true`。平局时直接查这个变量即可。
