# 《达芬奇密码》（Da Vinci Code / Coda）玩法规则与电子版实现说明

《达芬奇密码》是一款 2 到 4 人的公开推理桌游。每名玩家面前都有一排只对自己可见的数字牌，玩家通过观察顺序、已公开信息、他人的猜测结果，以及自己每回合新抽到的牌，逐步推断别人的隐藏数字。最后，场上唯一还保有至少 1 张未公开牌的玩家获胜。

这份文档的目标不是做“入门介绍”，而是把规则拆到足够实现电子版。文中会区分三类信息：

- `官方明确`：我能从现有规则页直接确认的内容。
- `官方 FAQ/二手转录`：规则镜像或转载中出现、但我没拿到原始官网页面的内容。
- `实现建议/推断`：为了做电子版必须补足的明确化决策。

---

## 一、我能确认到的版本范围

- 以 Winning Moves 英文版规则为主。
- 标准模式使用 `24` 张数字牌。
- 进阶模式额外加入 `2` 张横杠牌（dash / scramble / wild panel）。
- 玩家人数为 `2-4` 人。

不同地区版本的外观、名称、配色叫法可能不同，但核心机制一致。

---

## 二、游戏目标

`官方明确`

目标是让自己的密码序列尽可能晚被完全破解。  
当场上只剩下一名玩家仍拥有至少 `1` 张未公开的牌时，该玩家立刻获胜。

换成电子版判定条件就是：

- 玩家的牌列中，只要还有任意 `revealed = false` 的牌，这名玩家就仍然“存活”。
- 当 `alive_players == 1` 时，游戏结束。

---

## 三、组件与电子版数据结构

## 1. 实体组件

`官方明确`

- 深色牌 `13` 张：`0-11` 各一张，另有 `1` 张横杠牌。
- 浅色牌 `13` 张：`0-11` 各一张，另有 `1` 张横杠牌。
- 标准模式不使用两张横杠牌。

因此电子版最基础的牌库可以表示为：

```ts
type TileColor = "dark" | "light";

type Tile = {
  id: string;
  color: TileColor;
  value: number | null; // 0-11；横杠牌为 null
  isDash: boolean;
};
```

## 2. 玩家状态

电子版建议维护：

```ts
type PlayerTile = {
  tileId: string;
  revealed: boolean;
};

type PlayerState = {
  playerId: string;
  orderedTiles: PlayerTile[];   // 按当前牌列从左到右保存
  alive: boolean;
  pendingDrawTileId: string | null; // 当前回合开头抽到、尚未并入牌列的牌
  correctGuessCount: number;    // 若以后要支持锦标赛计分可直接复用
};
```

## 3. 全局状态

```ts
type GameMode = "standard" | "advanced";

type GameState = {
  mode: GameMode;
  drawPile: string[]; // tileId 列表
  players: PlayerState[];
  currentPlayerIndex: number;
  phase: "turn_start" | "guessing" | "choose_continue" | "game_over";
  winnerIds: string[];
};
```

## 四、准备阶段（Setup）

## 1. 组牌

`官方明确`

- 标准模式：移除两张横杠牌，只保留 `24` 张数字牌。
- 进阶模式：保留全部 `26` 张牌。
- 所有参与牌面朝下混洗。

电子版中不需要模拟“面朝下抓牌”的物理过程，直接在服务器端洗牌即可。

## 2. 初始发牌

`官方明确`

- `2` 人局：每人 `4` 张。
- `3` 人局：每人 `4` 张。
- `4` 人局：每人 `3` 张。

## 3. 初始排序

`官方明确`

每位玩家将自己起始手牌按从左到右升序排列：

- 数字小的在左，数字大的在右。
- 若数字相同，`深色牌（黑牌）必须在浅色牌（白牌）左侧`。

例如：

- `D1, D4, L7, L10` 是合法顺序。
- `D5, L5` 中，`D5` 必须在左边。

电子版应由系统自动排序，玩家不需要手动整理。

排序比较器可定义为：

```ts
function compareNumberTiles(a: Tile, b: Tile): number {
  if (a.value !== b.value) return (a.value ?? -1) - (b.value ?? -1);
  if (a.color === b.color) return 0;
  return a.color === "dark" ? -1 : 1;
}
```

## 4. 首位玩家

`官方明确`

最年轻的玩家先手，之后顺时针进行。

`实现建议`

线上房间通常拿不到真实年龄，建议改为：

- 房主指定先手，或
- 随机先手。

## 五、牌列规则

这一部分是电子版最容易写错的地方。

## 1. 公开牌与隐藏牌

`官方明确`

- 玩家自己的牌正面对自己可见。
- 对手只能看到牌背，除非该牌已经被公开。
- 一张牌被公开后，会一直保持公开状态，留在原来的位置上。

电子版中，`revealed = true` 的牌应永久公开给所有玩家。

## 2. 每回合新抽到的牌

`官方明确`

玩家在自己回合开始时先抽 `1` 张牌，但这张牌不会立刻并入自己的牌列，而是先作为“本回合线索牌”留在一旁，仅自己可见。

因此电子版要区分两类牌：

- 已在牌列中的牌
- `pendingDrawTileId` 指向的、尚未并入牌列的临时牌

## 3. 新牌并入牌列的时机

`官方明确`

- 如果玩家本回合猜错：这张刚抽到的牌要 `明置` 插入自己牌列。
- 如果玩家本回合猜对并选择停手：这张刚抽到的牌要 `暗置` 插入自己牌列。

## 4. 数字牌的插入位置

`官方明确`

普通数字牌插入后仍必须满足：

- 从左到右递增
- 同数时深色牌（黑牌）在左、浅色牌（白牌）在右

电子版应由系统自动找出唯一合法位置并插入。

## 六、标准模式回合流程

## 1. 回合开始：抽牌

`官方明确`

当前玩家先从剩余牌堆中抽取 `1` 张牌，形成自己的 `pendingDrawTileId`。

## 2. 进行一次猜测（Attack / Guess）

`官方明确`

玩家必须指定：

- 一个对手
- 该对手牌列中的一张 `尚未公开` 的牌
- 自己宣告的 `颜色 + 数字`

也就是说，猜测对象不是“某个位置大概是什么数”，而是明确宣告：

- “这是深色 1”
- “这是浅色 7”

电子版动作可以建模为：

```ts
type GuessAction = {
  targetPlayerId: string;
  targetTileIndex: number;
  declaredColor: "dark" | "light";
  declaredValue: number | "dash";
};
```

## 3. 猜对时的处理

`官方明确`

如果猜对：

- 被猜中的那张牌立刻公开。
- 当前玩家本回合可以继续猜下一张牌。
- 当前玩家也可以主动停止连猜。

如果主动停止：

- 将本回合抽到的 `pendingDrawTileId` 以 `暗置` 方式插入自己的牌列。
- 回合结束，轮到下一位玩家。

## 4. 猜错时的处理

`官方明确`

如果猜错：

- 当前玩家必须把本回合抽到的那张牌公开。
- 然后将它以 `明置` 方式插入自己的牌列。
- 当前回合立即结束。

这意味着：

- 猜错不会公开你原有的某张隐藏牌。
- 公开的是“你这回合刚抽到的牌”。

## 5. 连猜机制

`官方明确`

只要当前玩家上一猜正确，就可以继续猜，连续次数没有上限。  
但玩家在每一次猜对后都可以选择“停手保牌”，把抽到的新牌暗置并入自己的牌列。

这也是游戏的核心风险管理：

- 继续猜：可能多公开对手，但一旦失误，自己新增牌会明置。
- 见好就收：确保新增牌保持隐藏，但少一次继续进攻的机会。

## 6. 玩家出局

`官方明确`

当某位玩家的所有牌都已经公开时：

- 该玩家立刻出局。
- 该玩家不能再抽牌。
- 该玩家不能再猜别人的牌。

电子版判定：

```ts
player.alive = player.orderedTiles.some(tile => !tile.revealed);
```

## 7. 胜利

`官方明确`

当场上只剩一位仍拥有未公开牌的玩家时，游戏结束，该玩家获胜。

## 七、进阶模式（横杠牌 / Dash）

## 1. 进阶模式的额外牌

`官方明确`

进阶模式把两张横杠牌加入牌堆：

- `dark dash`
- `light dash`

## 2. 横杠牌的性质

`官方明确`

横杠牌是“wild panel”。规则明确允许它：

- 插入自己牌列中的任意位置
- 甚至可以放在 `0` 的左边
- 或放在 `11` 的右边

并且：

- 一旦横杠牌插入牌列，之后不能再移动

这条规则适用于两种时机：

- `初始发牌后整理牌列`：如果起始手牌里有横杠牌，玩家需要自己决定它放在哪个位置
- `回合中把横杠牌并入牌列`：无论是暗置并入还是明置并入，插入位置都由该玩家决定

## 3. 猜测横杠牌

`官方明确`

猜测横杠牌时，仍然必须报颜色：

- “这是深色横杠”
- “这是浅色横杠”

## 4. 电子版如何表示横杠牌位置

`实现建议`

横杠牌不参与普通数字排序；它更像一个“固定占位符”。  
因此电子版不要给横杠牌分配虚假的数值，比如 `-1`、`12` 或随机值，否则后续插牌会出错。

更稳妥的实现方式是：

- 横杠牌可以插入当前牌列的任意缝隙。
- 插入后只锁定“位置”，不锁定“数值区间”。
- 后续普通数字牌继续插入时，只要求“忽略横杠牌后，所有数字牌的相对顺序合法”。

因此进阶模式下，横杠牌的插入动作不应该做成全自动，而应做成：

- 玩家选择目标缝隙
- 服务器校验该位置合法
- 合法后锁定该位置

例如当前牌列是：

- `D3, dark-dash, L6`

之后摸到 `D5`，合法结果应为：

- `D3, dark-dash, D5, L6`

而不是因为横杠被当成某个具体数字而触发重排。

## 八、牌堆耗尽时的处理

这里是实现时必须明确、但主规则页写得不完整的部分。

`官方 FAQ/二手转录`

我找到的 Winning Moves 规则转录 FAQ 明确写到：

- 如果牌堆耗尽，游戏继续。
- 之后玩家轮到自己时不再抽牌，只执行猜测。
- 如果猜错，玩家需要公开自己的一张牌。

## 电子版建议规则

当 `drawPile.length === 0` 时：

1. 回合开始不再生成 `pendingDrawTileId`。
2. 玩家仍必须进行猜测。
3. 如果猜对，仍可继续连猜或结束回合。
4. 如果猜错，改为从自己当前仍隐藏的牌中选择 `1` 张公开，然后回合结束。

## 为什么要写成“选择 1 张”

`实现建议/推断`

FAQ 只说“reveal one panel of their own”，没有明确是：

- 系统指定哪一张
- 还是玩家自行选择哪一张

电子版最合理的实现是“由玩家自行选择一张自己的未公开牌公开”，因为：

- 官方主规则的惩罚本质是“暴露自己的信息”
- 当没有新抽牌可暴露时，选择自己的一张隐藏牌公开是最自然的替代
- 这也能让 UI/交互保持清晰

如果你更追求保守实现，也可以把这条做成房间选项。

## 九、电子版最小状态机

建议把一回合拆成以下状态：

## 1. `turn_start`

- 若牌堆非空，抽 1 张到 `pendingDrawTileId`
- 进入 `guessing`

## 2. `guessing`

- 当前玩家必须做一次合法猜测
- 若猜错：
  - 有 `pendingDrawTileId`：公开并明置插入
  - 无 `pendingDrawTileId`：公开自己一张隐藏牌
  - 检查出局/胜利
  - 切到下一玩家 `turn_start`
- 若猜对：
  - 公开对手该牌
  - 检查对手是否出局、是否已经决出胜者
  - 若游戏未结束，进入 `choose_continue`

## 3. `choose_continue`

- `continue`：返回 `guessing`
- `stop`：
  - 若有 `pendingDrawTileId`，暗置插入自己牌列
  - 清空 `pendingDrawTileId`
  - 切到下一玩家 `turn_start`

## 4. `game_over`

- 冻结所有操作
- 展示赢家与所有最终牌列

## 十、服务器校验规则

电子版应由服务器做权威判定，至少校验以下内容：

## 1. 猜测合法性

- 目标玩家必须仍存活
- 目标牌必须是未公开牌
- 不能猜自己
- `declaredColor + declaredValue` 必须是一个合法牌面

## 2. 插牌合法性

- 普通数字牌插入后，忽略已公开/未公开状态，只看牌面顺序，必须满足升序
- 同数时深色牌（黑牌）在左，浅色牌（白牌）在右
- 横杠牌插入位置一旦确定，不允许后续重排

## 3. 信息可见性

- 只有牌的拥有者和服务器知道未公开牌面
- 公开牌面对所有玩家广播
- `pendingDrawTileId` 只能发给当前玩家本人

## 4. 出局校验

- 任意一次公开事件后都立即检查该玩家是否还有隐藏牌

## 5. 胜利校验

- 每次有人出局后都重新统计 `alive_players`

## 十一、日志、回放与 UI 建议

这些不是官方规则，但对电子版非常重要。

## 1. 日志建议记录的字段

```ts
type TurnLog = {
  turnNo: number;
  actorPlayerId: string;
  drewTile: "hidden" | null; // 对其他玩家只显示是否有抽牌
  guess: {
    targetPlayerId: string;
    targetTileIndex: number;
    declared: string;
  };
  result: "correct" | "wrong";
  revealedTileOwnerId: string;
  revealedTileFace: string;
};
```

## 2. 是否自动记录历史猜测

`官方明确`

规则礼仪中明确写了“不能把自己的猜测记下来”，原版有记忆负担。

`实现建议`

电子版最好做成房间选项：

- `strict_memory = true`：不提供完整历史猜测面板，只显示当前公开牌
- `strict_memory = false`：提供完整操作日志，降低记忆负担

如果目标是尽量还原实体版，我建议默认 `true`。

## 3. 自动排序

电子版应始终自动维护牌列合法顺序，不要要求玩家拖拽调整数字牌顺序，否则容易引入无意义失误。

## 十二、实现时容易踩坑的边界情况

## 1. 不能攻击已公开牌

虽然规则文字没有专门列“禁止攻击已公开牌”，但这是从机制上显然成立的。  
电子版应直接禁用对已公开牌的点击。

## 2. 回合内可能连续淘汰多人

多人局中，某玩家连猜时可以连续公开多个对手的最后隐藏牌。  
每次公开后都要立即重算 `alive`，但只要场上存活玩家仍大于 `1`，当前玩家就还可以继续本回合。

## 3. 最后一击时手里仍有一张待并入的新抽牌

主规则没有清楚说明：如果你在持有 `pendingDrawTileId` 的情况下通过一记正确猜测直接赢得游戏，这张牌是否还要并入牌列。  

`实现建议`

最简单的做法是：

- 一旦胜利条件达成，立刻结束游戏
- 不再要求把 `pendingDrawTileId` 并入牌列

如果以后要支持锦标赛计分，再单独确认这一点。

## 4. 线上环境无法还原“抽牌时不小心翻开就必须拿走”

这条属于实体操作规则，电子版可忽略。

## 十四、可直接据此实现的结论

如果现在要做一个可玩的电子版，最小规则集可以直接定为：

- 支持 `2-4` 人
- 支持 `standard` 与 `advanced` 两种模式
- 标准模式：`24` 张数字牌；进阶模式：额外加入 `2` 张横杠牌
- 回合开始先抽 `1` 张牌；猜错则明置并入，猜对可连猜或停手暗置并入
- 场上只剩一名仍有隐藏牌的玩家时获胜
- 牌堆耗尽后继续猜；若猜错，则公开自己 `1` 张隐藏牌
- 默认采用“严格记忆模式”，不自动展示完整猜测历史

这套规则已经足够驱动服务端状态机、前端交互、日志系统和胜负判定。
