# Design 12.1: Store & Load 机制

## 目标与范围
- 提供“自动保存”开关；可在游戏开始前或游戏过程中开启。
- 一旦在当前游戏中开启自动保存，就不能再关闭（Checkbox 置灰为不可用）。
- 开启自动保存后，从下一个 `state_version` 开始，每次游戏状态变化都落盘到 `.data/${roomId}/${state_version}.save`。
- 提供 Load 对话框，列出所有可加载的游戏：roomId、游戏类型、参与玩家。
- 选择后创建一个新的房间（新 roomId），使用读到的状态作为初始状态。

## 状态与数据模型

### Room 增量字段
- `auto_save: bool`：是否启用自动保存（默认 false）。
- `state_version: int`：保存序号，直接复用 `room.state_version`（每次游戏状态变化 +1）。
- `source_room_id: Optional[str]`：可选，记录来源存档的 roomId。

### 保存文件结构
路径：`.data/<room_id>/<state_version>.save`

建议使用 JSON，字段如下（最小可用集）：
```
{
  "room_id": "abc123",
  "game_type": "cabo",
  "room_status": "in_game",
  "state_version": 12,
  "saved_at": 1735689600,
  "players": [
    {
      "player_id": "...",
      "name": "Alice",
      "seat": 0,
      "is_bot": false,
      "ready": true,
      "reconnect_token": "..."
    }
  ],
  "game_state": { ... }
}
```
- `socket_id` / `connected` 不保存；加载后默认离线。
- `reconnect_token` 可选保存；Load 房间仍要求走席位认领，不允许使用 token 直接重连。
- `room_id` 表示存档来源；Load 后会生成新 roomId。

## 自动保存流程

### 开关行为
- 默认 `auto_save=false`。
- 可在游戏过程中开启；开启后当局不可关闭（UI 置灰，服务端拒绝关闭请求）。
- 若在游戏进行中开启，不立即保存当前状态；从下一次 `state_version` 增加开始保存。

### 触发点
- 若 `auto_save` 在开局前已开启：`room:start` 成功初始化游戏后（`state_version = 1`）立即保存一次。
- `game:action` 或 bot 行动导致 `state_version` 增加后保存。
- 若游戏进入 `game_over`，仍保存该最终状态。

### 写盘策略
- 写盘函数：`_save_room_state(room)`。
- 确保 `.data/<room_id>/` 目录存在。
- 先写入临时文件（例如 `.tmp`），再原子重命名为 `<state_version>.save`，避免半写入文件。

## Load 列表与加载流程

### 列表（客户端弹窗）
- 新事件：`room:load_list`（client -> server），返回 `room:load_list`（server -> client）。
- 服务端遍历 `.data/` 下所有 room 目录：
  - 取文件名中最大的 `state_version` 作为最新快照。
  - 读取该快照中的 `room_id`（作为 `source_room_id`）/ `game_type` / `players` / `saved_at`。
- 返回结构示例：
```
{
  "saves": [
    {
      "source_room_id": "abc123",
      "game_type": "cabo",
      "players": [{"name": "Alice", "is_bot": false}],
      "saved_at": 1735689600,
      "state_version": 12
    }
  ]
}
```

### 加载
- 新事件：`room:load`（client -> server），参数 `{source_room_id}`。
- 服务端流程：
  1. 查找 `.data/<source_room_id>/` 的最新快照并解析 JSON。
  2. 校验 `game_type` 存在、`game_state` 可用。
  3. 生成新 `room_id`（例如 `_generate_room_id()`）。
  4. 构建 `Room`：
     - `room_id` 使用新生成值；`game_type`/`status`/`state_version` 从保存值恢复。
     - `source_room_id` 记录保存中的 `room_id`。
     - 玩家列表按保存值恢复 `player_id / name / seat / is_bot / reconnect_token / ready`。
     - 机器人保留原座位与名称。
     - 真人默认离线（`socket_id=None`，`connected=False`），名字用于席位提示。
  5. 写入 `ROOMS` 并广播 `room:list_update`。
- 返回 `room:load_result {ok, room_id (new), source_room_id, message?}`。

### 席位认领（Load 后进入）
- 新事件：`room:claim_seat`（client -> server），参数 `{room_id, seat, name}`。
- 服务端规则：
  - 仅 `source_room_id` 存在的房间允许认领。
  - 对于 `source_room_id` 房间，`room:join` 不创建新玩家，仅用于触发选座；`room:reconnect` 应拒绝或提示改用选座。
  - `seat` 必须存在，且对应玩家 `is_bot=false`、`connected=false`。
  - 成功后复用该玩家的 `player_id`，覆盖 `name`（使用当前输入名），并设置 `socket_id/connected`。
  - `seat` 编号来自保存数据；为选座 UI，需返回 `seat/name/is_bot/connected`（可扩展 `room:list` 或新增 `room:seat_list`）。
  - 返回 `room:claim_result {ok, room_id, player_id, message?}`，并推送 `room:state`/`game:state`。

### 客户端行为
- 自动保存 Checkbox 允许在游戏过程中开启；一旦开启，本局内显示为灰色不可关闭。
- 在大厅添加“Load”按钮，点击后拉取 `room:load_list` 并展示对话框。
- 对话框每条记录显示：sourceRoomId、gameType、玩家名（含 bot 标记）。
- 选择“Load”后发送 `room:load {source_room_id}`；成功后房间出现在列表中。
- 点击 Join（针对 Load 房间）先弹出“选座”对话框：
  - 展示所有真人席位（显示保存时的名字，仅作提示），机器人席位不可选。
  - 选择席位后发送 `room:claim_seat`，成功后使用新名字继续游戏。

## 错误处理与边界
- 存档目录不存在或空：返回错误提示或空列表。
- 保存文件缺失 / 解析失败：在列表中忽略或返回错误提示。
- `game_type` 不存在：加载失败并提示。
- 无保存记录：列表为空态提示。
- 席位认领失败：seat 不存在 / 已被认领 / 对应 bot / 房间无 `source_room_id`。

## 兼容性与配置
- 需要在 `.gitignore` 中加入 `.data/`，避免保存文件进入版本库。
- 可选增加最大保留快照数（例如只保留最近 N 个），但 MVP 可不实现。

## 测试建议（MVP）
- 保存：触发 `room:start` 与 `game:action` 后生成对应 `state_version` 文件。
- 列表：同一 room 多个快照时只返回最新一条。
- 加载：
  - 同一份存档可多次 Load，生成不同新 roomId。
  - 正常加载后 `ROOMS` 中状态、玩家信息、`state_version` 与快照一致。
  - 机器人保留座位；真人席位可被重新认领并覆盖名字。
