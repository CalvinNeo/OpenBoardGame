# 掼蛋 AI 审查与改进顺序（2026-09-19）

> 本文保留第一轮审查和初次接入 benchmark 的历史记录。后续以 `68e62ab` 为基线的策略修复、Git 内存加载、旧测试修改理由及实测结果见 [优化记录](guandan_optimization_68e62ab.md)；当前工具不再使用本文历史记录中的源码快照方式。

结论：优先处理信息边界、价值目标和多层决策重复，再用固定基线衡量每一步。继续追加窄场景规则，可能修复单个复盘，却无法说明整体是否更强。本轮加入 [benchmark](guandan_benchmark.md)，不修改线上策略，也不把新增测试数量当成强度提升。

## 源码中可确认的问题

检查对象为当前 `game/guandan.py`、`game/guandan_ai.py`，基础 git revision 为 `f65bef8b423adb357ef36c39dbaa34e69b92d3e1`。当前 AI 文件有 14,244 行、259 个顶层函数，其中 69 个函数名含 bonus/penalty；AST 中有 101 个不同的 `components["..."]` 字面量键。这些数字说明维护规模，不证明每条规则都错。

### 1. 正确的信息边界还没有建立

`GuandanGame.bot_move` 将收到的完整 state 直接交给 `_heuristic_best_action`。`_hand_state_value_components → _team_finish_score` 对每个玩家的 `hand` 调用 `_estimated_turns_to_finish`，读取其他三家的真实牌型；`_team_finish_score_with_turn_override` 同样如此。服务端调用也传完整 state。因此“搜索中有 determinization”不等于根节点启发式没有用暗牌。

影响：启发式、搜索与实际玩家可用的信息不一致；改进可能是在利用额外信息，也可能因为不同层看到不同世界而出现矛盾。普通牌例测试不容易发现这一点。

建议：正式引入 `Observation`（自己手牌 + 公开历史 + 各家张数）和 `Belief`，只有搜索内部才产生完整的模拟世界。根节点估值不得访问真实隐藏手牌。最小验收是：固定公开信息与随机流、置换别人暗牌，输出分布不变。新 benchmark 已对适配器验证这一点；线上修复应单独改动并评测。

### 2. 团队价值目标与真实输赢不完全一致

`_team_finish_score` / `_team_finish_score_with_turn_override` 用预测名次分配：

| 本队名次 | 当前启发式值 | 单局真实净升级收益 |
| --- | ---: | ---: |
| 1/2 | 8 | +3 |
| 1/3 | 5 | +2 |
| 1/4 | 2 | +1 |
| 2/3 | 1 | -1 |
| 2/4 | -2 | -2 |
| 3/4 | -6 | -3 |

启发式可以非线性，但当前值不是零和，尤其 2/3 仍是正分。`_minimax_value` 在 `phase != playing` 时调用 `_evaluate_state_for_bot`；后者仅对 `game_over` 返回显式终局 ±1000，普通 `round_end` 仍走启发式。该启发式读取已确定名次，但还叠加剩余手牌、完成手牌奖励等项，没有用单局终局收益替代。

影响：已经确定的一局输赢仍可能被结构/控制项改变尺度，搜索与训练未必在优化同一个目标。不能仅凭代码断言它造成了某一盘错误，但这是比单个阈值更优先验证的假设。

额外做了终局一致性探针：用 seed=123、打 2 的同一发牌，构造两个 `round_end` 状态，每局末名保留原手牌的前 8 张，其余手牌清空，补全 `seen_cards` 并更新结束记忆。从 p0（A 队）视角：

| 完成顺序 | 本队真实收益 | `_evaluate_state_for_bot` |
| --- | ---: | ---: |
| p2, p1, p3, p0（本队 1/4，自己末名） | +1 | -72.061 |
| p1, p0, p2, p3（本队 2/3，自己第二） | -1 | -54.064 |

当前 value 越高越好，这个构造例中输局反而较高。该探针不是完整对局强度证据，但直接说明已结束局面的估值没有遵守确定的团队收益顺序。

建议：先统一真实终局效用（例如上述净升级收益 / 3），在终局提前返回；非终局 value 预测同一个效用。结构、控制、走牌轮数成为预测特征，而非在已结束的对局里继续加分。NN、rollout、minimax 和 benchmark 应共享含义，benchmark 的计分实现保持独立以避免循环验证。

### 3. 一份战术偏好在多层拥有决定权

现在的调用链大致为：

```text
_list_hint_options
  → _rank_lead_options / _rank_response_options
  → _filter_overbomb_options
  → quick / detailed scoring
  → _should_use_mcts
  → root subset / fast paths / heuristic prior / leaf evaluation
  → _should_accept_mcts_override
```

`_candidate_actions` 已排序并按 limit 截断，搜索再次裁剪。`_should_use_mcts` 在无当前牌墩或队友领牌时直接返回 False；这使许多领出与协作决策不会在中盘得到 MCTS 检查。`_should_accept_mcts_override` 又用启发式分差和局部条件否决搜索结果。当前源码已有共享 tactical components、候选 reservoir 和成对采样改进，问题并不是各层完全没有复用，而是同一偏好仍能既删候选、又加分、又否决结果。

影响：启发式判断错时，搜索可能没有机会恢复；测到的“auto≈heuristic”也可能是搜索覆盖少或覆盖结果被拒绝，并不等于搜索算法本身无效。

建议：把合法性约束、可证明支配关系与策略偏好分开。只有前两者能永久删动作；经验偏好进入共享特征/先验。有限宽度按动作家族保留代表，pass 作为合法选项参与比较。搜索触发根据价值不确定性和局势重要性逐渐连续化；否决仅保留合法性和确切终局约束，其他保守程度用统一风险项表达，并通过消融确认收益。

### 4. 窄阈值和重复计分容易造成跳变

例如 `_short_enemy_bomb_takeover_bonus` 对敌方炸弹后剩余张数设置 `>8` 不触发、`<=8/6/4/2` 分层加分，还结合最小炸弹、余牌轮数和队友兜底。回应打分另有 `response_material`、`special_response_overuse`、`control_break_penalty`、`plan_alignment`、`soft_overbomb_prior` 等项。源码中已经出现对特定接管场景取消重复拆牌惩罚的补偿逻辑，这正说明计分口径需要统一。

问题不是“阈值必然不好”，而是目前缺少证据说明某条规则触发多少次、改变多少次选择、在相邻局面是否稳定、移除它的整体收益如何。几十个不同单位的奖励/惩罚相加后，局部修补容易影响别处。

建议：收敛到少量连续概念：本队跑完所需控制轮次、敌方抢先结束的概率、行动后能否维持/移交牌权、消耗控制资源的机会成本、拆结构的增量成本。每个概念只有一个来源，quick 与 detailed 使用相同特征定义、不同计算精度；不要只是把原函数搬到多个文件。新增规则需附触发覆盖率、边界扰动测试与消融结果。

### 5. 截止时间与随机性本身会改变策略

`_bot_select_play` 的 quick incumbent、bounded response、partial candidate 和截止处理会走不同选择路径；`_mcts_score_actions` 与残局粒子生成内部有无参数 `random.Random()`。仅 `random.seed(...)` 加固定发牌不能重现完整策略。

建议：评测同时区分固定计算量和实际产品限时，记录候选完成数、搜索完成深度、最终方法、超时率与 p95。先比较同一预算内的提升；提升如果来自更多计算，需要把代价一起报告。新 benchmark 的 worker 接管模块随机源和固定计时器，不更改生产代码。

### 6. 回归测试多不等于整体强

当前 `test_guandan_bot.py` 已有约一万行，另有 reviewed round、MCTS、记忆和 NN 测试。它们擅长保住已知情形，但大量“该局面必须选这个动作”的断言也可能固化原有偏好。NN 的候选与部分训练目标同样来自现有启发式/搜索，扩大模型无法自动消除候选缺失和目标偏差。

建议：保留合法性/信息隔离/终局正确性测试；战术坏例子按同一局面允许多个合理动作，并做牌面、级牌、座次与张数边界的扰动。全局强度最终看保留 seed 的实际对局，不能看测试通过数或模仿准确率。

## 下一轮实施顺序与验收

| 顺序 | 变更 | 如何确认有价值 |
| --- | --- | --- |
| 0（本轮） | 冻结源码基线，加入同牌换队 benchmark | 同版本轨迹对称、净收益为零；失败不计分；暗牌置换不影响观察 |
| 1 | 线上 Observation 边界；普通单局终局使用确切效用 | 暗牌不变性、24 种名次终局计分、与冻结版本分别在 public/full 条件对照 |
| 2 | 输出各层候选存活、门控、override 拒绝原因；按规则家族做消融开关 | 找出低覆盖、重复罚分、负收益的规则，而不是凭印象删除 |
| 3 | 收敛共享价值特征，减少经验性硬裁剪，保留动作家族 | 候选召回率、残局参考解、相邻局面稳定性、净收益及 p95 一起比较 |
| 4 | 统一 belief 的软证据与风险；逐步扩大有价值的搜索覆盖 | 相同粒子与固定计算量下比较，验证扩大搜索确实改变并改善决策 |
| 5 | 用真实收益训练 value，逐步训练 policy 排序并接搜索 | 对冻结 heuristic/auto 和历史 checkpoint 的独立对手池验收 |

每轮只改变一个层次，并保留上一版。开发集找问题，保留集做验收；按级牌、领出/回应、队友领牌、对手短手和残局分层定位退步。在根因和指标没有稳定前，暂不继续扩充窄场景规则或单纯扩大 NN。

## 本轮落地边界

新增的是可运行的评测工具与上述审查，已有策略行为未修改。工具支持 `auto/heuristic/greedy/random` 及源码快照，暂不加载 NN checkpoint，不模拟完整升级比赛。公开信息模式使用虚拟分牌适配旧接口，线上原入口仍需独立修复。小样本 smoke 只验证评测链路，不能作为策略提升证据。

## 本轮验证记录

- 新增 13 项 benchmark 测试通过；与原有 MCTS、memories、find_sf 合跑共 34 项通过。
- 原有 `tests.test_guandan_reviewed_round` 的 3 项中有 1 项失败：`test_bot4_does_not_feed_low_single_to_seven_card_enemy_after_taking_lead` 选了 `♦️4`，断言要求级牌对子或三张 9。单独重跑、在改动前冻结源码里重跑都复现。本轮没有改写断言或新增战术补丁来掩盖它。
- 同源 greedy 对冻结 greedy，`fixed`，3 对 / 6 盘：每对轨迹相同，胜率 50%，净收益 0。
- greedy 对 random，`fixed`，30 对 / 60 盘：胜率 91.7%（bootstrap 95% 区间 85.0%–98.3%），净收益 +2.617/盘（+2.283–+2.883）。这验证评测对明显强弱差异的区分能力，不是当前 auto 的改进证明。
- 当前 auto 对冻结 heuristic，`public` + `wall`、每步请求 100ms，3 对 / 6 盘：胜率 50%，净收益 -0.167/盘，95% 区间分别为 [0%, 100%] 和 [-3, +3]，结论为 `inconclusive`。auto 的耗时 mean/p95/max 为 125/189/2455ms，heuristic 为 82/166/294ms；低预算下超时明显，实际耗时也必须随强度报告。此结果仅为 smoke，不代表默认 2000ms 的产品表现。
