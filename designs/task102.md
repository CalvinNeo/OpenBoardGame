# Task 102 — 红色的门和杀人鬼的钥匙

## 1. 目标与版本

为现有 FastAPI / Socket.IO 房间接入 `red_doors`，英文名 `Red Doors and the Murderer's Key`，中文名采用“红色的门和杀人鬼的钥匙”。大厅可用“红色的门”、中文全名、英文名或 `red_doors` 搜索。**基础版已接入大厅：4–6 人、16 张牌。** 下文保留分阶段设计，实际交付记录见第 12 节。

规则版本以 **BLACK MAZE DEEP** 为目标：16 张基础牌、23 张进阶牌；官方提供 40 个难度组合。不要混用 2019 原版的 4–6 人信息与后续版本的完整内容，也不要把 39 张牌全部混在一起当作默认开局。[官方组件说明](https://www.yellowsubmarine.co.jp/hobbybase/game/reddoor/contents1.jpg)、[官方难度表](https://www.yellowsubmarine.co.jp/hobbybase/game/reddoor/level.htm)。

按以下顺序实施，每个阶段单独达到可玩、可验证的完成条件：

1. **基础版**：先完成 4–6 人、16 张基础牌的完整开局、秘密查看、身份变化、死亡、逃脱、结算、机器人及保存恢复。
2. **少人数模式**：按作者规则加入 2–3 人的“胆小鬼”NPC；这不是普通机器人，也不能用一个会正常开门的机器人替代。
3. **进阶版**：逐张确认 23 张进阶牌，再开放依赖这些牌的官方难度；完整核对前，不显示可选择的 Lv 2–40 或未经验证的卡牌开关。
4. **额外内容**：“尖叫的陷阱”促销牌独立核对、独立开关，不计入 39 张标准牌。自定义组合属于可选后续功能，必须限制在已实现的牌内。

首个可玩交付可以明确标为 `Base rules · 16 cards`；只有少人数模式完成后才把注册人数下限从 4 改为 2。不能把基础版交付写成“完整 40 级”。

### 3.1 开门与身份

- 全体玩家开始时没有杀人鬼身份、没有道具。按座位方向依次行动；起始玩家默认房间首席，这是线上替代“最近看过恐怖电影的人”的选人方式，在 Help 中注明。
- 当前玩家从场上暗牌中选一张，只给本人显示牌面。明置牌不能再作为普通开门目标；别人或自己看过又盖回的暗牌可以重访。
- 普通玩家必须遵守牌面；只有明确允许放回的牌才可放回。杀人鬼有隐藏处理的特殊权限，但必须区分普通开门、效果造成的偷看，以及扩展明确写出的强制例外。
- 第一次取得杀人鬼钥匙的流程必须完成“获得钥匙、身份改变”；不能在已经窥见该牌后，用刚获得的身份撤销这次取得。
- 杀人鬼身份与钥匙是两个不同字段。钥匙回场、被移除或持有人死亡，均不能直接把身份重置。其他人后来取得回场的杀人鬼钥匙，可以产生第二名杀人鬼。
- 玩家声称“空房”不能被系统标成真或假；别人的面板、日志颜色、动作名称和处理阶段均不得暗示其真实身份。

身份保留与可重访的边界见[作者 Q&A](https://humaoz.wixsite.com/ozplanning/q-a-akaitobira)。

### 3.2 第四把钥匙与洗牌

基础模式下，玩家面前总共出现第四把钥匙时，立即进入匿名回收流程：收起已取得的钥匙，移除杀人鬼钥匙，将银钥匙放回场地，再把场地所有牌重新暗置洗牌。玩家保留身份；不公开哪位玩家原来持有被移除的钥匙。[官方流程图](https://www.yellowsubmarine.co.jp/hobbybase/game/reddoor/contents3.jpg)。

程序不能只是对原牌 ID 数组重新排序：

1. 服务端保留内部实例 ID，用于牌守恒和存档。
2. 每次场地洗牌递增 `board_epoch`，重新分配对外 `door_id`。
3. 旧门号、旧选择、旧门号对应的个人记忆失效；客户端收到统一的“迷宫已重排”提示。
4. 回场的持有物同样换对外 ID；公开的移除牌只提供牌种与数量，不输出可关联原持有人的实例 ID。
5. 只洗场上的牌及本次明确回场的牌；其他玩家仍持有的道具不会一起洗掉。
6. 场上之前明置的线索等重新暗置，之后再次开到可以重新生效。

同一次效果引起多人死亡或多个物品回场时，先完成整批区域移动，再统一洗牌，避免中途广播泄密。

### 3.3 死亡、保护与胜负

- 死亡者跳过行动，按规则将持有物放回场地；身份仍保留。死亡不让客户端获得其他人的私密信息。
- 防弹背心的防御与道具回场分别处理；不能因为免死便取消陷阱要求的其他后果。[作者陷阱 Q&A](https://humaoz.wixsite.com/ozplanning/q-a-akaitobira)。
- 只有一名普通玩家存活时仍须继续寻找出口；不能直接判其获胜。若最后一人取得杀人鬼钥匙，可转为杀人鬼独胜。
- 出口成功：检查所需钥匙，满足条件后，按牌面结算所有非杀人鬼玩家胜利。不要擅自把这一条件缩成“只有持钥匙的人赢”或“死亡平民必输”。
- 出口失败：混入杀人鬼钥匙，按规则结算杀人鬼阵营胜利。
- 独存胜利：一名杀人鬼成为唯一存活者时，该杀人鬼单独获胜；两名杀人鬼仍活着时，不能仅因为普通玩家都死了就结束。
- 全员死亡时显示 `No winner`。结算输出明确的 `ending_reason` 与 `winner_ids`，不能用“好人输了”反推某个固定胜者。
- 最终结算公开身份与胜负依据，并固定停留；不自动重新发牌或关闭结果。

上述三类结局的区别见[官方胜利条件图](https://www.yellowsubmarine.co.jp/hobbybase/game/reddoor/contents2.jpg)；扩展引入复活、身份翻转或额外结局后，必须按对应卡面重新核对优先级。

## 4. 状态机与动作接口

采用仓库现有 `GameDefinition` 与 `turn_mode="turn"`，不另建通信协议或独立游戏服务器。

| 阶段 | 谁能操作 | 下一步 |
| --- | --- | --- |
| `choose_door` | 当前存活玩家 | 选择一扇当前 epoch 的暗门 |
| `resolve_door` | 开门者 | 私下读牌，执行强制效果或作牌面允许的选择 |
| `choose_target` | 当前效果指定的玩家 | 点选门／持有物／玩家；无合法目标按已核实规则处理 |
| `private_result` | 取得私密结果的人 | 阅读并 `Continue`；不靠三秒自动计时消失 |
| `public_review` | 全部房间玩家 | 回顾公开效果，再统一继续 |
| `round_end` | 全部房间玩家 | 看结局，全部点击 `Next Round` 后开始下一局 |
| `game_over` | 无游戏动作 | 用户结束整场或返回房间；保留最终结果 |

**对外阶段需要裁剪**：未公开的效果在其他人视图中一律显示 `resolving`，不发送 `killer_choice`、`private_trap` 等可推断牌面的阶段名。`choose_target` 只有对应牌已依法公开时才展示公开含义。

### 4.1 回顾与 Next Round

本游戏原版是一局短局，没有固定的“全桌走一圈结算”。不要为了满足前端规范，擅自增加每圈洗牌、发资源或公开全部身份的规则。

适配 [FRONTEND.md](../FRONTEND.md) 的方式：

- 一次完整逃脱尝试视为一局／一轮。结局确定后进入 `round_end`，保留全桌结算，不立刻重开。
- 所有房间席位，包括本局已经死亡的玩家，分别点击 `Next Round`；机器人只确认自己，胆小鬼 NPC 不占确认席位。断线真人不会被自动确认，房主不能一键代替所有人确认。
- 等待期间允许每个席位选择下一步 `Play again` 或 `Finish`。任一玩家请求 `Finish` 时，本次共同确认的目标变为结束；任何目标变更清空已有确认，防止玩家批准了不同结果。全部确认后执行同一个目标。
- 房间机器人调度器只在 `in_game` 且 `game_over == False` 时工作。因此 `round_end` 仍保持这两个条件，直到全员确认 `Finish` 后才设置最终 `game_over`；不能提前关掉机器人，再等待机器人的确认。
- 陷阱／射击／匿名回收等重要公开结算，使用 `public_review` 原位停留，全部席位点击 `Continue` 后继续下一位。没有公开事件的普通暗置放回，无需插入全员等待。
- 私下看牌的等待只让本人确认，其他玩家只看到“正在处理”，不看见私密结果。

这是线上回顾节奏，Help 要与实体规则区分；它不改变牌效果、胜利条件或信息公开范围。

### 4.2 动作建议

所有动作走既有 `game:action`；以下是内部协议，不让玩家输入 JSON。

| 动作 | 参数 | 服务端检查 |
| --- | --- | --- |
| `open_door` | `door_id`, `board_epoch`, `turn_id` | 当前玩家、当前轮次、暗牌、未持有待处理效果 |
| `resolve_door` | `choice`, `turn_id` | 只接受该私有待处理状态允许的选项 |
| `choose_target` | `target_id`, `effect_id` | 目标区域、存活状态、是否允许自己、目标是否仍有效 |
| `ack_private` | `effect_id` | 只允许私密结果的接收者确认 |
| `ack_review` | `review_id` | 一人一次，必须对应当前公开回顾 |
| `set_next_mode` | `mode`, `review_id` | 仅结局回顾阶段，变更清空旧确认 |
| `next_round` | `review_id` | 仅本席位确认，全部确认后才重置或结束 |
| `claim` | `door_id`, `board_epoch`, `claim` | 可选的公开口头声明辅助；内容作为“声称”，不核实真假 |

动作 Schema 使用 `oneOf`、必填字段、枚举和 `additionalProperties: false`。模块自己再次校验，不能因为请求带 `skip_validation` 就允许非法动作。先验证或在副本处理，成功后提交；错误不改变随机状态、道具、身份或回合。

对已经看过的门，关闭 Help 或私有详情弹窗只影响显示，不撤销开门；只有尚未提交的本地选择可以用空白／Esc 取消。未完成的强制效果始终在行动面板保留入口，不能通过关弹窗跳过。

## 5. 后端状态、隐私与机器人

### 5.1 状态结构

`game/red_doors.py` 提供与现有游戏一致的 `init_game`、`get_legal_actions`、`apply_action`、`get_public_view`、`bot_move`、`serialize`、`deserialize`。

建议状态包含：

- `schema_version`、`rules_version`、已选配置、私有随机源与洗牌计数。
- `players`：席位元数据、存活、真实身份、已公开身份信息、持有物；明确区分“已知其曾是杀人鬼”与当前真实身份。
- `cards`：稳定内部 ID、牌种、区域、所有者、正反面；单一事实来源，避免库存和棋盘各保存一份牌造成复制。
- `board_epoch`、当前对外门号映射、玩家自己的合法观察记录。
- `round`、`turn_id`、`turn_order`、`current_turn`、私有 `pending_effect`、连锁效果队列。
- `review_id`、公开结果快照、`ready_player_ids`、下一局选择与结局。
- 公共事件和私有观察记录分开存储；只保留有限条活动日志。

随机源只在服务端／受控存档中保存。重新连接和读取公共视图不能重新洗牌。序列化使用 JSON 可表示数据与深拷贝，恢复时检查版本、区域引用和牌数量守恒。

### 5.2 可见性矩阵

| 信息 | 本人 | 其他玩家／观众 |
| --- | --- | --- |
| 尚未查看的场地暗牌 | 牌背与门号 | 牌背与门号 |
| 本人本次打开的暗牌、线索偷看结果 | 可见 | 不发送牌种、说明、可推断的事件 |
| 本人持有的暗钥匙 | 可见 | 仅钥匙背与数量；依法翻开后才公开 |
| 其他玩家已明置道具、明置场地牌 | 可见 | 可见 |
| 真实身份 | 本人可见 | 仅已依法公开的身份信息；不能按当前隐藏变化自动更新 |
| 随机种子、牌库／重排映射、内部 ID | 不发送 | 不发送 |
| 终局快照 | 全部身份与结局依据 | 相同终局公开信息 |

`get_public_view` 必须通过白名单构造，不能先复制完整 state 再零散删除字段。未取得权限的内容也不能藏在 `data-*`、DOM、资源 URL、tooltip 或 Explain 文案里。

特别处理现有接入点：

- `app.py::_emit_game_state` 当前大部分游戏会把同一份 `events` 发给每个玩家。新模块的返回事件只放公开中性通知，私密结果放在按 viewer 裁剪的 view；确需私密事件时再做明确的按玩家过滤。
- `app.py::_public_bot_action` 仅隐藏参数仍可能暴露动作类别。新游戏的私有处理动作统一广播为中性 `resolve`，不能公开 `ignore_trap`、`become_killer` 或藏匿选择。
- `room:state.game_config` 不能广播调试 seed；新增规则选项只放公开配置，测试种子不在普通 UI 出现。
- 旁观接口只返回公开信息；当前房间代码主要向席位玩家发视图，不能未经实现与验证便声称已有独立旁观入口。
- 死亡者保持原席位与自己的合法历史观察，不获得全知视图；复活也不重新抽取其身份。

### 5.3 机器人

机器人入口可以接受服务端 state，但立即转为与本人相同的裁剪视图，实际决策函数只接收该视图。

- 普通玩家优先探索未知门、获取钥匙、核验可疑钥匙，在有条件时尝试出口；尽量避免已知陷阱。
- 杀人鬼根据自己知道的信息选择隐藏效果、误导或使用攻击道具；不能读取别人的真实角色或未见的门。
- 私有记忆按 `board_epoch` 失效；公开声明仅作为不可靠线索。
- 所有强制选目标、私密结果确认、公开回顾、下一局确认都有机器人动作；死亡机器人仍能确认自己应参与的回顾。
- 不通过“超出 N 回合判某方赢”掩盖死锁。完整对局测试设步数上限只是检测失败，不是新增游戏规则。

## 6. 2–3 人规则

按[作者少人数规则](https://humaoz.wixsite.com/ozplanning/q-a-1)，增加一个胆小鬼 NPC：从三张银钥匙和一张杀人鬼钥匙中，随机暗置一张给它，其余牌正常入场。NPC 没有 socket、ready 或普通机器人思考回合，不开门。

需要选择时，由其后一个玩家代作决定；失去最初的钥匙时立即死亡。其钥匙可以成为检查与逃脱相关目标，但操作者不能预先看到 NPC 的真实钥匙。

实施前补充核对并写成明确用例：第四把钥匙回收是否触发 NPC 失钥死亡、NPC 后一位已死亡时的代理顺序、只剩非杀人鬼 NPC 时如何收束。资料没有明确写出的边界要记录为待核实，不能悄悄发明平局或自动逃脱。

NPC 计入规则中玩家／存活者的哪一类判定，应从少人数原文逐项映射，不能将房间真人数量和规则参与者数量混用。确认门始终只计算实际房间席位。

## 7. 进阶内容

### 7.1 数据与实现方式

`game/red_doors_data.py` 保存牌的英文 ID、中文／日文名、类型、数量、说明、资料来源、效果实现键及适用难度。未实现的牌不会进入 `enabled_cards`。另外保存按名称核对过的 `LEVEL_PRESETS`，避免用截图中的排版位置或疑似印刷错误编号建立引用。

官方 40 级表使用 20 类常规进阶牌；“迷宫的秘密”“教团的魔导书”“道化之灯”三张不在该难度梯度里。促销牌再独立处理。[官方难度图](https://www.yellowsubmarine.co.jp/hobbybase/game/reddoor/contents4.jpg)。

逐张核验重点按机制拆开：

| 机制 | 涉及示例 | 实现重点 |
| --- | --- | --- |
| 信息查看／公开 | FBI 手册、数字刺青、监控室 | 查看对象、可见人群、之后是否公开、身份信息是否过期 |
| 攻击／保护 | 神经瓦斯、杀人鬼之斧、军人匕首、无声毒蛾、防毒面具 | 攻击时机、保护范围、是否穿透、防御品消耗与死亡顺序 |
| 身份／复活 | 有尸体的房间、面具的低语、返魂之香、道化之灯 | 当前身份和历史身份分离，复活座位恢复，重复触发 |
| 钥匙／出口 | X 光照片、门卡、守护之键、出口之影 | 实物钥匙与替代钥匙分离，死亡条件、数量门槛、二次结局 |
| 强制连锁 | 束缚具房间、手铐、教团的魔导书、迷宫的秘密等 | 代理决策、多目标、杀人鬼可否跳过、连锁中的结局优先级 |

此表用于安排代码与测试，不代表已经确认了每张卡的全部效果。不要用同一条“杀人鬼忽略所有效果”分支覆盖有强制措辞的扩展牌。

### 7.2 已确认的配置例外

- Lv 1：仅 16 张基础牌。
- Lv 2：基础牌加 FBI 手册；Lv 3：基础牌加数字刺青。难度是指定组合，不是把前一级新增牌继续累加。
- Lv 26、27、33、34：基础牌中银钥匙减少一张，再加入该级指定牌。不能只加“守护之键”而忘记移出一张银钥匙。
- Lv 40：基础牌加“出口之影”“有尸体的房间”“危险的窥视孔”“神经瓦斯”。
- 难度图中部分军人匕首编号与其他行不一致；导入时按牌名匹配并复核实体编号，禁止把 X 光照片误识别为匕首。

每个开放的等级必须验证：牌数、银钥匙数量、依赖效果均已实现、机器人能处理其全部选择、存档能恢复其待处理效果。

### 8.1 文件与作用域

- 复用房间连接、错误提示、存档流程；切换游戏时清除本游戏选择、计时器、私有详情、tooltip 和 Explain 模式。

### 8.2 视觉与布局

原创暗色迷宫桌面：炭灰背景、酒红门牌、暖白文字、银色钥匙与少量琥珀色动作强调。门牌用 CSS 矩形门框、门把手和编号绘制；不开启闪屏、强制音效或自动播放恐怖素材。

桌面采用“迷宫主区 + 本人行动侧栏”，玩家条紧邻迷宫；下方活动日志限制高度并内部滚动。主界面仅显示当前目标、本人身份短提示、合法动作和必要计数，大段规则放入 Help。

| 区域 | 内容 |
| --- | --- |
| 顶部状态 | 当前玩家、局数、存活人数、已持有钥匙背数量；隐藏钥匙不显示银钥匙精确总数 |
| 迷宫 | 自适应门牌网格；每门有当前编号、暗／明状态、本人合法记忆标记 |
| 本人区 | 私有身份、持有钥匙真面与明置道具、当前打开的牌、必要目标选择 |
| 玩家条 | 姓名、席位、存活状态、明置道具、暗钥匙背、依法公开的信息 |
| 回顾区 | 当前公开后果／终局依据、已确认人数、尚未确认姓名、继续按钮 |
| 日志／笔记 | 限高日志；可选个人笔记默认收起，不把私密笔记写入公共日志 |

手机以 320px 为最窄验收宽度重新排版：基础迷宫优先四列紧凑牌背，牌面说明放在完整宽度的当前操作区；扩展牌增加行数，不把字缩到不可读。需要时使用 `Board` / `My cards` 页签，行动与选中的牌保持相邻。

- 禁止页面横向滚动，也禁止容器内文字、Emoji、图片溢出或相邻重叠。使用 `min-width: 0`、`minmax(0, 1fr)`、换行和合适尺寸；不能仅靠 `overflow: hidden` 裁掉关键信息。
- 长玩家名、长牌名、满道具栏重新换行；同一组主／次按钮尽量一行两列，有合理间距。
- 若提供笔记，手机优先右侧可开关 dock；打开时采用重排或完整切换面板，不能覆盖仍可操作的门牌。笔记只属于当前玩家。
- 门牌点击即可完成，基础版不需要拖拽或平移。后续若加入可拖拽地图，仅在地图区域使用 `touch-action: none`，配合 pointer capture、up／cancel 清理及拖后抑制点击；区域外保留页面滚动。
- 非游戏内容 UI 使用英文：`Help`、`Explain`、`Close`、`Cancel`、`Confirm`、`Continue`、`Next Round`、`Notes` 等。卡牌、身份和规则解释可以使用中文。

### 8.3 点选与提交

点击暗门只做本地选中，在门牌上层的足够大容器内显示 `Open` / `Cancel`；点空白或 Esc 取消，不增加 `Clear Selection`。提交 `Open` 后再取得私密牌面，不能先让客户端预览所有候选门。

选目标同样采用点玩家／道具／门，再在相邻行动区确认；如卡片过小，就在上层容器显示操作，不能让蒙版按钮挤出牌面。开枪、挑战出口的确认写明已知后果，不显示服务端才知道的成功概率或隐藏目标身份。

配置采用下拉框和贴近同行的 checkbox／label，不要求键入 JSON。网络等待禁用重复提交；收到新 `turn_id`、`effect_id` 或 `board_epoch` 时清理过期选择并重新渲染。

### 8.4 Help 与 Explain

完整遵守 [task40.md](task40.md)：

- `Help` 打开规则对话框，包含开局、牌表、身份、区域移动、结局、少人数／扩展适用范围和线上确认节奏。
- `Explain` 用捕获阶段拦截原操作；只有有解释的控件显示虚线高亮和问号光标，其他控件外观不变，但不能继续执行原动作。
- disabled 按钮仍可解释：使用 `pointerdown` 与可见控件矩形的坐标命中，不能只绑定 `click`。
- 查看一次解释后自动退出；Esc 退出解释模式。Help／Explain 自身及弹窗关闭保留正常行为。
- 弹窗支持 Esc、`Close`、遮罩关闭与焦点恢复；解释弹窗不改变已选择的门或目标。
- 暗门 Explain 只能解释“如何开门／当前公开状态”，不能因该门实际是陷阱而给出不同文案。私有牌的说明只从本人 view 生成。

### 8.5 Emoji、缩写与即时提示

全程统一显示名称和图标，例如银钥匙（🔑）、杀人鬼的钥匙（🗝️）、防弹背心（🦺）、线索（🔎）。不能在 Help 只写名称，主界面却只给无说明图标；颜色也配文字或形状，不只依赖色觉。

没有游戏操作功能的图标、徽标、缩写提供简短提示；可操作元素通过 Explain 点选解释：

- 对本身没有游戏操作的图标／徽标，桌面鼠标悬停、键盘聚焦出现 tooltip。
- 手机轻点这些非操作图标显示浮动提示，3 秒后消失；连续点击切换为最新说明并重新计时。不添加独立 `ⓘ`，可操作门牌、按钮与区域说明通过 Explain 点选查看。
- 不在可执行按钮旁添加说明入口。Explain 模式下点击按钮只解释、不提交、不取消当前选择；禁用按钮也可点选解释。
- 滑动不触发点击提示；提示限制宽高、贴合视口，不越界、不挡住必须操作的区域；显式浮层只在阅读说明时出现。
- 游戏切换、重排、打开对话框、进入 Explain 时清理旧提示，避免旧身份或旧牌面残留。

## 10. 实施与验收

### 10.1 规则模块

1. 16 张牌初始化、数量守恒、实例只在一个区域、错误人数与配置拒绝。
2. 普通开门只能选暗牌；线索偷看不执行陷阱、不取得钥匙、不改变角色。
3. 普通玩家不能跳过强制效果；杀人鬼的合法隐藏选择不在对手日志中露出。
4. 杀人鬼钥匙取得、移除、回场再取得、多人杀人鬼与死亡后身份保留。
5. 第四把钥匙回收不暴露原持有人；场地重新暗置，held items 与 removed cards 各自正确。
6. 催眠瓦斯在零道具时仍移除和洗牌；陷阱不被错误移除；所有洗牌更新外部 ID 并拒绝旧请求。
7. 防弹背心的一次防护和其他后果；射击完整结算顺序、无枪不能射击、拒绝不合法目标。
8. 出口可放回后重访；不足钥匙不能挑战；三银成功／混入杀人鬼钥匙失败／独存杀人鬼／非杀人鬼独存继续／全员死亡。
9. 私密查看、目标选择、公开回顾、结局回顾每个阶段保存与恢复后行为一致。
10. 一个人确认不能推进；重复／过期确认不计数；断线真人不被跳过；死亡玩家与机器人按本人席位确认。
11. 非法类型、伪造目标、错误 epoch／turn／effect、观众请求及 `skip_validation` 都不能部分改变状态。
12. 同一裁剪视图下，替换对手暗牌／真实身份后机器人决策不变；决策不得依赖完整 state。

少人数和进阶阶段各自增加专用测试；不能用基础版测试通过来宣称扩展已验证。多个种子的 4／5／6 人机器人对局运行至结局；少人数开放后加入 2／3 人。测试的步数上限触发时报告未终止原因，不篡改胜负。

### 10.2 Socket.IO 集成

- 两个以上真实会话开局、私下看牌、检查钥匙、得到私密线索结果；同时检查所有 `game:state.view`、`events`、机器人事件与 `room:state`。
- 构造只有身份／暗牌不同的两个状态，比较未获授权观察者的消息；合法的公开行为发生前，不应有数据差异。
- 重连至私有结果和确认阶段，验证自己的信息恢复、他人的信息不泄露、已确认状态保留。
- 机器人不在普通“等待别人看牌”时越权；所有确认完成后才恢复后续处理。

### 10.3 浏览器与布局

使用真实本地房间验证从创建到最终结算的流程；规则边界通过固定局面补充展示，不把注入视图的截图当成完整真实对局证明。

- 1440px 桌面、768px、375px、320px 检查：页面无横向滚动，所有可见文字、图片、Emoji 在容器内，面板间无覆盖。
- 最长玩家名、六人满道具、扩展最多门牌、长日志、长牌面、结局多名胜者均需检查。
- Help 开关、Esc、焦点恢复；Explain 禁用按钮命中、只高亮有解释项、阻止原动作、一次退出。
- 桌面 hover／focus，手机点击三秒消失／连续点击更新／滑动不触发；说明操作不提交游戏动作。
- 选门确认、点空白取消、Esc 取消、网络等待防重发、洗牌清掉过期选择；关闭规则弹窗不能取消已经发生的开门。
- 回顾不被刷新或机器人自动跳过；本局死亡玩家仍看到需要自己确认的入口。
- 截图与浏览器结果写入 `tmp/task102/`，检查控制台没有新增脚本错误。

## 11. 规则核验记录与后续边界

以下条目要解决在对应功能开放之前，避免无依据的程序默认值：

1. **基础射击已核验**：对照[发行商子弹房间／背心补充牌面](https://www.yellowsubmarine.co.jp/hobbybase/game/reddoor/contents5.jpg)与[可辨读的实体手枪／背心照片](https://cdn-ak.f.st-hatena.com/images/fotolife/x/xyoshixaki/20210919/20210919005243.jpg)：命中者归还全部持有物；有背心则移除背心、免死，其他物品仍回场。子弹房间连同场地重洗；牌文未要求射击者归还手枪，只有它因射击者被命中等效果回场时才失去。目标写作“一名玩家”，未排除自己，因此允许自选。依据照片中的实体牌文，不以文章概括代替规则。
2. **看破已核验**：[发行商实际游玩中的牌面照片](https://assets.st-note.com/production/uploads/images/24400289/picture_pc_b21eaf591bf6eb154221e7e6025da18a.jpg)明确允许公开或不公开。无目标时可直接暗置放回；公开效果牌留场。按当前发行商 BLACK MAZE DEEP 补充说明，目标限定其他人的暗钥匙，已明置银钥匙不可再选。移除的是杀人鬼钥匙，而不是看破本身。
3. **少人数边界**：第 6 节的 NPC 失钥、代理人死亡与只剩 NPC；明确后才能承诺 2–3 人完整可玩。
4. **23 张进阶牌**：逐张效果、数量、强制措辞、相互作用与结局优先级；难度表只确认了配牌，不确认这些效果。
5. **促销牌**：独立核对“尖叫的陷阱”及中文牌名对应，不把论坛玩家自制修改当作官方规则。

完成基础核验后先实现基础完整闭环；其余机制按证据逐步加入。每次开放功能，都在本文件追加实际支持范围、验证结果与截图链接，保留来源和未解决项，不把计划写成完成记录。
