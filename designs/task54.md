# 《环中物语》（Things in Rings）电子版规则与系统设计文档

> 说明：本文基于公开可访问的官方规则书与官方商品页整理。凡是官方明确写出的内容，我按“官方规则”描述；凡是为了落地电子版而必须补充的实现细节，我会明确标记为“电子版实现约定”。

---

## 1. 游戏概述

《环中物语》（Things in Rings）是一款基于隐藏规则、分类推理和连续试探的桌游。桌面上会摆出 1 到 3 个相互重叠的圆环，每个圆环都代表一种规则类型：

- **词汇（Word）**：看“这个物品名称怎么写、怎么拼、怎么读”。
- **属性（Attribute）**：看“这个物品本身具有什么物理性质”。
- **情景（Context）**：看“这个物品通常会在什么场景里出现、被使用”。

其中 1 名玩家担任**出题人 / Knower**，只有他知道每个圆环背后的隐藏规则；其余玩家是**猜题人 / Finders**，轮流把“物品卡”放进某个区域，试图推断这些隐藏规则。

### 1.1 基本信息

- **人数**：2 到 6 人
- **时长**：约 20 分钟
- **官方基础组件**：
  - 3 个圆环
  - 3 个圆环标签（Word / Attribute / Context）
  - 240 张 Thing Cards（物品卡）
  - 24 张 Word Rule Cards（词汇规则卡）
  - 24 张 Attribute Rule Cards（属性规则卡）
  - 24 张 Context Rule Cards（情景规则卡）

### 1.2 核心体验

- 猜题人并不需要完整说出规则文本，只要能据此把手牌都正确放完，就能获胜。
- 同一回合中，只要当前玩家持续放对，他就可以一直继续放牌。
- 一旦放错，出题人会把这张牌移动到正确位置，该玩家补 1 张牌并立即结束回合。

## 2. 核心概念与电子版数据结构

电子版应当以“规则判定 + 区域定位”作为核心。

### 2.1 圆环类型

电子版建议定义：

```ts
type RingType = "word" | "attribute" | "context";
```

### 2.2 规则卡对象

```ts
interface RuleCard {
  id: string;
  type: RingType;
  text: string;
  difficulty?: "easy" | "normal";
  evaluationMode: "auto" | "knower";
  evaluatorSpec?: Record<string, unknown>;
}
```

说明：

- `type`：规则所属的圆环类型。
- `text`：规则卡显示给出题人的原始文本。
- `evaluationMode`：
  - `auto`：系统可直接判定，适合词汇类。
  - `knower`：需要出题人裁定，适合属性/情景类。
- `evaluatorSpec`：仅给可自动判定的规则使用，例如“至少 7 个字母”“没有重复元音”等机器可执行条件。

### 2.3 物品卡对象

```ts
interface ThingCard {
  id: string;
  name: string;
  imageUrl?: string;
  canonicalWord?: string;
  canonicalPhonetics?: string[];
  metadata?: Record<string, unknown>;
}
```

说明：

- `name`：物品名称。
- `imageUrl`：卡面插画，用于帮助出题人按“典型/平均版本”理解物品。
- `canonicalWord` / `canonicalPhonetics`：如果要自动判定词汇规则，需要机器可读的拼写/发音数据。

### 2.4 玩家对象

```ts
interface PlayerState {
  id: string;
  name: string;
  seatIndex: number;
  role: "knower" | "finder";
  hand: string[];
  connected: boolean;
}
```

### 2.5 圆环与区域对象

电子版不要把“区域”写死成坐标判断，而应当抽象成**布尔组合**。

假设本局启用了 `N` 个圆环，则每张牌对每个圆环都会得到一个布尔值：

- `true`：符合该圆环规则，在该环内部
- `false`：不符合该圆环规则，在该环外部

于是整张牌的最终区域就是一个位掩码：

```ts
interface Zone {
  id: string;           // 例如 "001"、"101"
  bitmask: number;      // 例如 1、5
  activeRingCount: 1 | 2 | 3;
}
```

示例：

- 1 环局：共 2 个区域
  - `0`：环外
  - `1`：环内
- 2 环局：共 4 个区域
  - `00`：两个环都不进
  - `01`：只进第 1 个环
  - `10`：只进第 2 个环
  - `11`：两个环都进
- 3 环局：共 8 个区域
  - `000` 到 `111`

### 2.6 公共游戏状态

```ts
interface ThingsInRingsState {
  phase:
    | "lobby"
    | "setup"
    | "seed_clues"
    | "finder_turn"
    | "await_knower_judgement"
    | "round_transition"
    | "ended";
  mode: "competitive" | "coop";
  ringTypes: RingType[];
  rings: {
    ringIndex: number;
    type: RingType;
    ruleCardId: string;
  }[];
  players: PlayerState[];
  currentPlayerId?: string;
  thingDeck: string[];
  discardPile: string[];
  boardCards: {
    thingCardId: string;
    zoneId: string;
    source: "clue" | "play";
    placedBy?: string;
  }[];
  winnerPlayerId?: string;
  pendingJudgement?: {
    playerId: string;
    thingCardId: string;
    proposedZoneId: string;
    unresolvedRingIndexes: number[];
  };
}
```

## 3. 官方规则还原

### 3.1 选择本局使用几个环

官方支持 1 环、2 环、3 环三种难度：

- **1 环**：轻松/家庭局
- **2 环**：标准局
- **3 环**：进阶局

官方首次游戏建议：

- 优先使用 **Attribute + Word**
- 如果带小孩，可以只使用 **Attribute**
- 熟悉后可任意组合

注意：官方只有 3 种环类型，因此一局中不会出现两个同类型的环。

### 3.2 竞技模式（Competitive）初始化

适用于 3 到 6 人。2 人时官方建议改玩合作模式。

初始化顺序如下：

1. 选择本局启用的环类型，摆成相互重叠的 Venn Diagram。
2. 指定 1 名玩家为出题人（Knower），其余都是猜题人（Finders）。
3. 将每种已启用的规则卡单独洗混。
4. 出题人从每个已启用的规则牌堆中各抽 1 张，秘密查看。
5. 官方首局建议只使用带有“Easy”标识的规则卡。
6. 洗混 Thing 牌堆。
7. 出题人抽 5 张 Thing Cards，从中选 3 张作为**初始公开线索**，按真实规则放到桌面正确区域，剩余弃掉。
8. 每名猜题人各抽 5 张 Thing Cards。
9. 出题人左手边的猜题人先手。

#### 3.2.1 初始线索的意义

这 3 张公开线索是本局最重要的推理起点。

- 它们已经被正确放入了某个区域。
- 这些线索本身不说明完整规则，只说明“这 3 个物品在当前隐藏规则下应该落在这些区域”。
- 猜题人要结合这些线索、其他玩家的错误修正、以及自己后续的成功/失败摆放来推理。

### 3.3 竞技模式回合流程

猜题人按顺时针轮流行动。

在某个猜题人的单回合内：

1. 从手牌中选择 1 张物品卡。
2. 将它放到一个具体区域：
   - 放进某个环内
   - 放在多个环的重叠区域
   - 放在所有环外
3. 出题人检查该摆放是否正确。
4. 若正确：
   - 该牌留在桌面上
   - 当前玩家继续再放 1 张牌
5. 若错误：
   - 出题人将该牌移动到正确区域
   - 该牌仍然留在桌面上
   - 当前玩家从 Thing 牌堆补 1 张牌
   - 当前玩家回合立刻结束

#### 3.3.1 单回合的本质

这是一个“连续冲刺直到出错”的结构，而不是“一回合只出一张牌”。

因此电子版必须支持：

- 同一玩家在一个 turn 中连续多次提交摆放
- 一旦第一次出错就强制终止该回合

### 3.4 竞技模式胜利条件

当任意猜题人在自己的回合中，把手里最后 1 张牌也正确放出，而且**没有因为这次摆错而补牌**，则该玩家立即获胜。

换言之：

- **获胜条件**：手牌数从 `1 -> 0`，且此次摆放正确
- **不是获胜**：手牌打空后又因摆错补 1 张

官方还提到：胜者出现后，大家可以尝试口头猜测这些隐藏规则，作为“炫耀权”内容；这不是正式计分的一部分。

### 3.5 出题人的官方职责

官方对出题人的定位很重要：

- 出题人的职责是**主持与裁定**，不是故意刁难其他玩家。
- 出题人可以在任何时候重新查看秘密规则。
- 出题人不能泄露规则内容，哪怕在合作模式中也不能直接说出口。
- 当一张牌是否符合某条规则存在解释空间时，应按“这个物品的**典型/平均版本**”去判断。
- 可以参考卡面插图来缩小解释范围。

这说明《环中物语》官方规则本身就允许一定主观裁量，尤其是属性和情景规则。

### 3.6 合作模式（Co-op Variant）

官方合作模式适用于 2 到 4 人。

#### 3.6.1 合作模式目标

- 出题人和所有猜题人同队
- 目标是让**每一名猜题人**都成功放完自己 5 张牌

#### 3.6.2 合作模式初始化变化

在合作模式中，以下内容与竞技模式不同：

1. 出题人抽 **10 张** Thing Cards，而不是 5 张。
2. 出题人先摆出**每位玩家 1 张线索**，并且官方明确写了“包含出题人自己”。
   - 因此电子版应按总人数计算初始线索数。
   - 例如 3 人合作局，初始线索数就是 3。
3. 出题人将剩余 Thing Cards 留在自己手中；这些牌不用于争胜，而是作为后续补充线索的库存。
4. 每名猜题人依然各拿 5 张手牌。

#### 3.6.3 合作模式进行方式

1. 所有猜题人依次行动，和竞技模式一样：连续放牌直到首次出错。
2. 一整轮猜题人回合结束后，出题人再摆出 **1 张新线索**。
3. 猜题人之间可以讨论、交流策略。
4. 猜题人的手牌在打出前保持隐藏。
5. 已经没有手牌的猜题人跳过自己的后续回合。

#### 3.6.4 合作模式胜负

- 如果出题人需要再放 1 张线索，但自己手里已经没有线索牌可放，则全队失败。
- 如果所有猜题人都先于这个时点清空手牌，则全队获胜。

## 4. 电子版判定引擎

这一节是把桌游规则翻译成可编码逻辑。

### 4.1 核心判定公式

对任意一张 Thing Card，系统要针对每一个启用环求值：

```ts
membership[i] = doesThingFitRule(thingCard, ringRule[i]);
```

其中：

- `membership[i] = true` 表示这张牌属于第 `i` 个环内部
- `membership[i] = false` 表示它不属于第 `i` 个环

然后把所有布尔值按顺序编码成 zone：

```ts
zoneId = membership.map(v => (v ? "1" : "0")).join("");
```

例如在三环局中：

- `101` 表示：
  - 属于第 1 个环
  - 不属于第 2 个环
  - 属于第 3 个环

玩家提交的区域与真实 `zoneId` 一致，则判定为正确；否则错误。

### 4.2 为什么电子版要按“逐环求值”而不是直接存区域

因为：

1. 玩家看到的是“环规则”，不是“区域标签”。
2. 三种环类型的判断来源不同：
   - 词汇：更适合自动判定
   - 属性：更适合人工裁定
   - 情景：更适合人工裁定
3. 电子版需要记录“为什么某牌落在这个区域”，否则后续无法解释、回放或复盘。

因此建议为每次摆放保存一份裁定记录：

```ts
interface JudgementRecord {
  thingCardId: string;
  ringIndex: number;
  result: boolean;
  source: "auto" | "knower";
  ruleCardId: string;
}
```

## 5. 电子版状态机

建议使用如下状态机：

```text
lobby
  -> setup
  -> seed_clues
  -> finder_turn
  -> await_knower_judgement   (仅当存在人工裁定环时)
  -> finder_turn / round_transition
  -> ended
```

### 5.1 `lobby`

- 玩家进入房间
- 选择模式：`competitive` / `coop`
- 选择启用环：1~3 个
- 可选项：是否只使用 Easy 规则
- 房主开始游戏

### 5.2 `setup`

系统完成：

- 指定出题人
- 从对应规则牌堆抽取秘密规则
- 洗 Thing 牌堆
- 发手牌
- 进入线索布置阶段

### 5.3 `seed_clues`

#### 竞技模式

- 出题人从自己抽到的 5 张 Thing 中选 3 张作为线索
- 系统计算/收集这些线索的真实归属区域
- 自动放到正确位置

#### 合作模式

- 出题人从自己的 10 张 Thing 中选出 `player_count` 张初始线索
- 系统计算/收集其真实归属区域
- 自动放到正确位置
- 剩余手牌保留在出题人手里，供后续每轮追加 1 张线索

### 5.4 `finder_turn`

当前猜题人可以重复执行：

1. 选择手牌
2. 选择目标区域
3. 提交
4. 系统判定

如果这一手完全可自动判定，则立即给结果：

- 正确：从手牌移除，牌上桌，继续同回合
- 错误：从手牌移除，牌上桌到真实位置，补 1 张，结束回合

如果这一手存在需要人工裁定的环，则进入 `await_knower_judgement`。

### 5.5 `await_knower_judgement`

仅出题人可见裁定面板。

系统将：

1. 对所有可自动判定的环先求值。
2. 找出所有需要出题人判断的环。
3. 逐个向出题人询问“该牌是否符合这条规则”。
4. 汇总为真实 `zoneId`。
5. 返回 `finder_turn` 继续处理结果。

### 5.6 `round_transition`

仅合作模式需要。

- 当所有尚未清空手牌的猜题人都完成了本轮行动后：
  - 若出题人还有线索牌：出 1 张新线索，然后开始下一轮
  - 若出题人已无牌可出：游戏结束，合作失败

### 5.7 `ended`

- 显示胜者 / 团队胜负
- 公开所有秘密规则
- 可显示完整裁定记录与操作回放

## 6. 出题人角色优化方案

这是本需求最关键的改动。

### 6.1 官方问题

官方规则把所有规则的最终解释权都交给出题人，这在实体桌游里没有问题，但在电子版里会带来两个问题：

1. **词汇类规则本来是可以机器判定的，却还要人点一次，效率低。**
2. **属性/情景类规则天然主观，但如果不保留出题人裁定，又会失去原作味道。**

因此推荐把出题人的职责拆成两层：

- **词汇环**：系统自动裁定
- **属性环 / 情景环**：由出题人裁定

### 6.2 优化后的判定原则

#### 6.2.1 词汇（Word）

**系统直接给出答案，不经过出题人。**

原因：

- 词汇类规则本质是确定性条件。
- 只要卡牌数据库里有可机器处理的名称/拼写/发音信息，系统就可以稳定得出 `true/false`。
- 这部分不需要保留主观裁定空间。

电子版建议：

- 所有 `type = "word"` 的规则卡都必须带 `evaluationMode = "auto"`。
- 后端直接根据 `canonicalWord`、`canonicalPhonetics` 等字段计算结果。
- 对玩家只公开“最终落点”，不额外公开某个词汇环究竟是 `true` 还是 `false`，以避免泄露过多中间信息。

#### 6.2.2 属性（Attribute）

**交给出题人判断是否符合。**

原因：

- 许多属性规则不是离散事实，而是“典型情况下是否成立”。
- 官方规则明确允许出题人按“典型/平均版本”做判断。

电子版建议：

- 当牌被提交后，系统弹出仅出题人可见的裁定框：
  - 当前牌名/插画
  - 当前属性规则文本
  - 两个按钮：`符合` / `不符合`
- 出题人的选择只影响该牌在该环上的布尔值，不直接单独公示。

#### 6.2.3 情景（Context）

**同样交给出题人判断是否符合。**

原因：

- 情景类规则通常最依赖文化语境、使用场景、常识边界。
- 官方规则也明确指出这是最难的一类。

电子版建议与属性环相同：

- 当前牌提交后
- 由出题人判断它是否属于该情景规则
- 系统据此计算最终区域

### 6.3 优化后的完整裁定流程

假设本局启用了三个环：

- Ring A = Word
- Ring B = Attribute
- Ring C = Context

某玩家打出 `banana` 并选择区域 `111`。

系统处理顺序建议为：

1. 自动计算 Word 结果，例如 `A = true`
2. 向出题人询问 Attribute：`B = ?`
3. 向出题人询问 Context：`C = ?`
4. 组合出真实区域，例如 `101`
5. 若玩家选的不是 `101`，则判错并自动把牌移动到 `101`

这能在保留原作主观性的前提下，把出题人操作压到最少。

### 6.4 进一步优化建议

#### 6.4.1 仅启用词汇环时，允许“无出题人模式”

如果本局只启用 1~3 个词汇可自动判定的环，则实际上不再需要人工出题人。

可选实现：

- 系统直接抽秘密规则
- 所有玩家都是猜题人
- 服务器作为隐藏裁判

这会让纯词汇局变成完全自动化的推理游戏。

#### 6.4.2 出题人裁定要留痕

对于属性/情景类规则，建议把每次裁定都记录下来：

- 哪张牌
- 哪条规则
- 出题人判为符合/不符合
- 时间戳

目的：

- 方便断线恢复
- 方便赛后回放
- 出现争议时可复盘

#### 6.4.3 对外只显示“最终区域”，不显示逐环判定

如果把每个环的 `true/false` 单独公开给所有玩家，信息量会远高于原桌游。

因此推荐：

- 公开信息：牌最终被摆到哪个区域
- 隐藏信息：本次在每个主观环上的单独判断结果

这样最接近实体桌游体验。

---

## 7. 电子版 UI / 交互要求

### 7.1 桌面区域

前端应当提供固定的 Venn Diagram 布局：

- 1 环：1 个圆 + 外部区域
- 2 环：双环重叠布局
- 3 环：三环标准布局

每个区域必须可点击或拖放。

### 7.2 信息可见性

#### 出题人可见

- 当前所有秘密规则
- 所有待裁定请求
- 出题人手牌（竞技模式的 5 张中仅用于选线索；合作模式中则是线索库存）

#### 猜题人可见

- 圆环类型标签（Word / Attribute / Context）
- 所有已经上桌的公开牌及其所在区域
- 自己手牌
- 当前轮到谁

#### 不应公开

- 其他猜题人手牌
- 秘密规则文本
- 属性/情景类规则的逐环单独裁定结果

### 7.3 回合反馈

玩家提交一张牌后：

- 若正确：轻量确认动画，允许继续出牌
- 若错误：卡牌自动移动到正确区域，并明确提示“回合结束，补 1 张牌”

### 7.4 合作模式专属反馈

- 清楚显示“当前是第几轮猜题人回合”
- 在每轮结束后，播放“出题人新增 1 张线索”的动画
- 显示出题人剩余线索数

## 8. 官方未明确、但电子版必须决定的实现约定

以下不是我从公开官方规则中直接拿到的，而是为了落地实现给出的合理默认值。

### 8.1 牌堆耗尽

公开规则没有明确写到 Thing 牌堆耗尽时如何处理。

电子版建议默认：

- **不洗回弃牌堆**
- 如果玩家因摆错需要“补 1 张”，但主牌堆为空，则不补牌，直接结束回合

理由：

- 基础牌数 240 很大，常规对局几乎不至于耗尽
- 不洗回更接近“信息持续积累”的体验

### 8.2 出题人超时

官方桌游没有超时概念，但电子版应防止卡局。

电子版建议：

- 属性/情景裁定默认 20 秒
- 超时后自动提醒
- 长时间无响应时由房主或系统接管，或者终止对局

### 8.3 初始线索是否合法性检查

电子版建议对出题人摆出的每张线索都做服务器端记录：

- 词汇环部分由系统自动判定
- 属性/情景环部分由出题人给出裁定

这样初始线索也能进入统一的数据流，不会变成“只靠前端摆上去”的脏数据。

## 9. 无法获取的游戏资源

如果目标是**尽量忠实复刻官方内容**，目前公开可获取信息还不够，至少还缺下面这些资源：

1. **240 张官方 Thing Cards 的完整卡库**
   - 公开页面只展示了少数示例卡。
   - 若要完整复刻，需要全部卡名、卡图、卡牌唯一 ID。

2. **72 张官方规则卡的完整文本**
   - 目前公开可见的是数量和少数示例，不是完整牌库。
   - 需要：
     - 24 张 Word 规则全文
     - 24 张 Attribute 规则全文
     - 24 张 Context 规则全文

3. **哪些规则卡属于 “Easy” 的完整标记**
   - 官方规则书提到首局建议使用 Easy 规则。
   - 但公开资料中没有看到完整的 Easy 卡清单。

4. **词汇规则的机器可执行元数据**
   - 如果要按你要求把“词汇”类型改成系统自动裁定，就必须有：
     - 官方物品名称的标准拼写
     - 必要时的发音/音节/字母结构数据
   - 公开资料没有给出这类结构化数据。

5. **官方中文本地化资源**
   - 如果电子版界面想用中文，并且仍然保留官方 Word 规则逻辑，就会遇到问题：
     - 很多 Word 规则是基于英文拼写/发音设计的
     - 不能直接翻成中文后继续成立
   - 因此若要做中文版，通常需要重新设计一套中文词汇规则卡组。

6. **官方高清卡图与美术资源**
   - 公开商品页只能看到宣传图与少数局部图。
   - 若前端要还原原版视觉，需要正式授权素材。

7. **官方扩展/赠品卡的完整资料**
   - 商品页提到 Pop Culture Promo Pack，但未公开完整卡单。
   - 如果要支持扩展，也需要额外获取对应内容。

### 9.1 一个非常重要的现实问题

即使拿到了完整规则卡文本，**属性**与**情景**这两类规则也依旧不能被“完全客观自动化”。

原因不是缺算法，而是官方规则本身就把这两类规则的一部分解释权留给了出题人，允许按“典型/平均版本”判断。

因此：

- **词汇**：可以做成系统自动裁定
- **属性 / 情景**：推荐继续保留出题人裁定，这正是你要求的优化方向

## 10. 结论：推荐的电子版实现路线

如果目标是尽快把《环中物语》做成能玩的电子版，我建议这样实现：

1. **先完成玩法引擎**
   - 支持 1~3 环
   - 支持竞技 / 合作
   - 支持区域位掩码判定
   - 支持回合内连续出牌直到首次出错

2. **把出题人优化为“半自动裁判”**
   - Word 自动判定
   - Attribute / Context 人工裁定

3. **内容层先允许自定义题库**
   - 在未拿到完整官方卡库前
   - 可先实现自定义 Thing 卡与自定义规则池

4. **若未来要忠实复刻官方版，再补正式资源**
   - 官方 Thing 全卡库
   - 官方 Rule 全卡库
   - Easy 标记
   - 英文词汇判定数据
   - 正版美术
