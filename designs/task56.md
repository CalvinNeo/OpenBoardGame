# 《Bohnanza: Das Würfelspiel》规则与电子版实现说明

## 1. 适用范围与资料来源

本文只针对 **2022 年 AMIGO 版《Bohnanza: Das Würfelspiel》**（商品号 `02253`）整理规则，适用人数 **2–5 人**。  
不要和 **2012 年旧版《Würfel Bohnanza》** 混淆。旧版常见差异包括：骰子数量更多、每张任务卡的订单更多、胜利分数更高。

本说明主要依据：

- 官方英文规则 PDF：<https://blog.amigo-spiele.de/content/ap/rule/02253-GB-AmigoRule.pdf>
- 官方德文规则 PDF：<https://blog.amigo-spiele.de/content/ap/rule/02253-DE-AmigoRule.pdf>
- 官方商品页：<https://www.amigo-spiele.de/kartenspiele/bohnanza-das-wuerfelspiel_2253_1194>
- 一张清晰展示“概览卡/Overview Card”的实物照片，用于还原骰子六面分布：<https://www.jungundaltspielt.de/bohnenkniffel-bohnanza-das-wuerfelspiel-von-amigo-rezension/>

其中：

- **回合流程、收获、终局**来自官方规则。
- **5 颗骰子的具体面分布**并未在规则文字里列成表，我是根据清晰实物照片中的概览卡还原的。
- **55 张收获卡的完整牌库**官方规则没有逐张列出，因此这部分仍是缺失资源。

## 2. 游戏概述

每位玩家面前有两张公开的收获卡（`Harvest Card / Erntekarte`）：

- 上面那张是当前正在推进的 **当前卡 / Top Card**
- 下面那张是用来遮挡进度的 **覆盖卡 / Bottom Card**

当前卡上有 **5 条订单（orders）**，必须 **自下而上** 依次完成。  
玩家在自己的回合不断掷 5 颗豆子骰，每次掷完都必须至少把 1 颗骰子放进公共 **豆田（bean field）**，其余骰子可以继续重掷。  
其他玩家会在你每次掷骰后，立即检查 **刚刚掷出的那些骰子** 是否能帮助他们完成自己当前卡的最底部未完成订单。

当一个玩家在自己的当前卡上完成了：

- 3 条订单：可随时收获，得 1 分
- 4 条订单：可随时收获，得 2 分
- 5 条订单：可随时收获，得 3 分

游戏目标是：**在终局结算后拥有最多的 Bohnentaler（豆币）**。  
官方触发条件是：**某位玩家在一次收获后达到 10 或更多豆币**，然后进入最终结算阶段。

## 3. 组件与固定数据

## 3.1 组件

- 55 张收获卡
- 5 张概览卡（玩家辅助卡）
- 5 颗豆子骰
- 1 个豆子人形标记（`bean piece`）
- 1 个豆田区域（印在盒盖内侧）

## 3.2 六种豆子类型

为了避免“豆种名字”和“图标底色”混淆，电子版建议使用稳定的内部代码。

| 代码 | 英文名 | 建议中文名 | 图标底色 |
| --- | --- | --- | --- |
| `blue` | Blue Bean | 蓝豆 | 蓝色 |
| `red` | Red Bean | 红豆 | 粉红色 |
| `soy` | Soy Bean | 大豆 | 紫色 |
| `stink` | Stink Bean | 臭豆 | 棕色 |
| `green` | Green Bean | 绿豆 | 橙色 |
| `garden` | Garden Bean | 花园豆 | 绿色 |

注意：

- **`green`（Green Bean）** 的图标底色是 **橙色**
- **`garden`（Garden Bean）** 的图标底色是 **绿色**

实现时应以内部代码为准，不要直接拿颜色名当豆种名。

## 3.3 骰子分布

本游戏有两种骰子模板：

- **深色骰 2 颗**
- **浅色骰 3 颗**

根据概览卡实物图，还原如下：

| 骰子模板 | 数量 | 六个面 |
| --- | --- | --- |
| 深色骰 | 2 | `blue`, `garden`, `stink`, `stink`, `soy`, `soy` |
| 浅色骰 | 3 | `stink`, `red`, `blue`, `blue`, `green`, `green` |

合计 5 颗骰子的 30 个面频次：

| 豆种 | 总出现面数 |
| --- | --- |
| `blue` | 8 |
| `stink` | 7 |
| `green` | 6 |
| `soy` | 4 |
| `red` | 3 |
| `garden` | 2 |

这也解释了为什么 `garden` 很稀有。

## 4. 收获卡结构与订单表示法

## 4.1 一张收获卡包含什么

每张收获卡有：

- 5 条订单，必须从下往上完成
- 右侧的若干小数字：表示首掷达成概率，仅用于参考，不参与规则结算
- 正反两面：
  - 正面：订单
  - 反面：1 枚豆币

## 4.2 订单的图形语法

从官方例子和实物牌面可归纳出至少以下几种表示法：

### A. 单色圆标

表示“需要 1 颗指定豆子”。

例如：

- `blue`
- `red`

### B. 多个圆标并列

表示 **AND**，每个圆标都要有 1 颗对应骰子满足。

例如：

- `blue + red + garden`
- `blue + blue + soy`

### C. 双色分割圆标

表示“这个位置可以由两种豆子之一满足”。

例如：

- `(soy | green)` 表示这一格可以是 `soy` 或 `green`
- `(garden | red)` 表示这一格可以是 `garden` 或 `red`

### D. 斜杠 `/`

表示左右两组是 **整组二选一**。

例如：

- `blue + blue + blue + blue / red + red`
  - 表示要么 4 个 `blue`
  - 要么 2 个 `red`

### E. 同一订单内部每个圆标都需要独立占用 1 颗骰子

虽然规则明确说“骰子不会在不同订单之间被消耗”，但**在同一条订单内部**，每一个圆标都代表一个独立需求位。

因此，订单判定不能只靠“包含关系”；要做“多重集合/匹配判定”。

## 4.3 官方规则给出的四个订单示例

官方示例可以抽象为：

1. `stink + soy + red`
2. `green + green  /  soy + soy`
3. `(soy | green) + red + garden`
4. `(soy | green) + (garden | red) + (garden | red)`

第 4 条在文字上写作“先有 1 个 soy/green，再从剩余骰子里有 2 个 garden/red”。  
由于两组候选豆种互不重叠，实现上可以直接写成上面的 3 槽需求。

## 4.4 建议的数据结构

```ts
type Bean = "blue" | "red" | "soy" | "stink" | "green" | "garden";

interface OrderSlot {
  allowed: Bean[]; // 单图标时长度为 1；双色图标时长度为 2
}

interface OrderAlternative {
  slots: OrderSlot[]; // 这一组是 AND
}

interface Order {
  alternatives: OrderAlternative[]; // 多组之间是 OR
}

interface HarvestCard {
  id: string;
  ordersBottomToTop: [Order, Order, Order, Order, Order];
  probabilities?: [number, number, number, number, number]; // UI 可选
}
```

## 4.5 建议的订单判定算法

因为一条订单最多只会用到 5 颗骰子，最简单可靠的办法是 **回溯/DFS**：

1. 取当前可用骰子的结果数组，例如 `["blue", "red", "red", "garden"]`
2. 对订单的每个 `alternative` 分别尝试
3. 对当前 alternative 的 `slots` 逐个匹配
4. 每匹配一个 slot，就临时占用 1 颗尚未占用的骰子
5. 有任意一个 alternative 可以全部匹配成功，则该订单完成

不要把“不同订单之间不消耗骰子”误写成“同一订单里也不消耗骰子”。

## 5. 开局设置

1. 洗混 55 张收获卡，形成面朝下牌堆。
2. 每位玩家抽 2 张，**都公开**放在自己面前：
   - 上面一张作为当前卡（`top card`）
   - 下面一张作为覆盖卡（`bottom card`）
3. 将 5 颗骰子和豆子人形标记放到中央。
4. 将豆田区域置于全体可见。
5. **最后一个吃过豆子的人** 先手，并拿到豆子人形标记。

电子版实现建议：

- “最后一个吃过豆子的人”在线上无法可靠判断，建议改成：
  - 随机先手；或
  - 房主指定先手
- 两张起始卡都应公开显示

## 6. 回合流程

## 6.1 总体原则

当前持有豆子人形标记的玩家是 **主动玩家**。  
在其回合中：

- 主动玩家只能在**所有骰子都放入豆田后**，检查自己的当前卡
- 其他玩家则会在**主动玩家每一次掷骰后**，用“刚刚掷出的骰子”检查自己的当前卡

## 6.2 主动玩家的标准回合

### 阶段 A：初始化

- 取回豆田中的 5 颗骰子
- 将本回合的 `reroll_used = false`
- 清空本回合的 `bean_field = []`

### 阶段 B：掷骰循环

重复以下流程，直到 5 颗骰子都被放进豆田：

1. 掷出当前所有“尚未放入豆田”的骰子，得到 `current_roll`
2. 所有非主动玩家立即用 `current_roll` 自动检查自己的当前卡
3. 主动玩家可以选择是否使用豆子人形标记的“整批重掷”
4. 若选择重掷：
   - 本回合只能用这一次
   - 必须把 **刚刚掷出的全部未锁定骰子** 重新掷一次
   - 豆田里已锁定的骰子不能拿回
   - 所有非主动玩家再用新的 `current_roll` 检查一次自己的当前卡
5. 主动玩家必须从这一次最终保留的 `current_roll` 中，至少选 **1 颗** 放进 `bean_field`
6. 其余未锁定骰子进入下一轮继续掷

### 阶段 C：主动玩家结算自己的当前卡

当 5 颗骰子全部进入 `bean_field` 后：

1. 主动玩家用 `bean_field` 里的全部 5 颗骰子
2. 从自己当前卡的**最底部未完成订单**开始
3. 能完成就覆盖
4. 继续检查新的最底部未完成订单
5. 直到遇到第一条不能完成的订单为止

### 阶段 D：结束回合

- 将豆子人形标记传给左手玩家
- 下一位玩家拿起豆田中的 5 颗骰子，开始新回合

## 6.3 最大投掷次数

因为共有 5 颗骰子，且每次正常结算后必须至少锁定 1 颗：

- 最多有 **5 次正常掷骰结算**
- 外加 **1 次整批重掷**

所以电子版可把“一个回合内的投掷事件数上限”安全地设为 **6 次**

---

## 7. 非主动玩家如何利用别人的骰子

这是本游戏最关键的互动点。

## 7.1 非主动玩家只能使用“刚刚掷出的骰子”

官方规则明确写到：

- 非主动玩家在每次掷骰后进行检查
- 但**不能使用之前已经放进豆田的骰子**

因此，非主动玩家的可用集合永远是：

- `current_roll`

而不是：

- `bean_field`
- `current_roll + bean_field`

## 7.2 检查顺序

对每个非主动玩家：

1. 读取其当前卡
2. 只看“最底部尚未完成的订单”
3. 如果 `current_roll` 可满足，则把覆盖卡向上推一格
4. 再继续检查新的最底部未完成订单
5. 重复，直到当前 `current_roll` 不能继续推进

因为所有玩家都是对着自己的公开卡、用同一组 `current_roll` 独立判定，所以电子版可以 **自动同时结算**，不需要逐个询问“是否完成订单”。

## 7.3 主动玩家的重掷会让其他玩家再获利一次

如果主动玩家使用了整批重掷：

- 其他玩家先对**第一次结果**检查一次
- 再对**重掷后的结果**检查一次

这两次都可能让别人推进订单。

## 8. 收获（Harvesting Beans）与得分

## 8.1 什么时候可以收获

只要某位玩家的当前卡上已经完成了 **3 条或更多订单**，他就可以 **随时** 收获：

- 可以在自己回合收
- 也可以在别人回合收

这意味着电子版必须允许 **回合外的可选动作：`HARVEST`**

## 8.2 收获得多少分

按当前卡已完成订单数结算：

| 已完成订单数 | 收获分数 |
| --- | --- |
| 3 | 1 豆币 |
| 4 | 2 豆币 |
| 5 | 3 豆币 |

## 8.3 收获步骤

若某玩家决定收获：

1. 将当前卡翻到背面，作为 **第 1 枚豆币**
2. 若本次应得 2 或 3 分，则从牌堆再抽 `得分 - 1` 张牌，作为额外豆币
3. 将这些豆币公开放到自己面前
4. 原本的覆盖卡上移，成为新的当前卡
5. 再从牌堆顶公开抽 1 张，作为新的覆盖卡
6. 立刻检查这张“新当前卡”是否已经能完成底部订单；若能，则继续覆盖推进

## 8.4 收获后的立即连锁

收获后，新当前卡可能会立刻再推进，甚至又达到 3 条已完成。  
规则允许玩家再次收获，因此电子版应支持 **连续收获（chain harvest）**。

## 8.5 “立即检查新当前卡”应使用哪组骰子

这是电子版最需要明确的一点。

### 官方明确的部分

- 非主动玩家平时只能用 **刚刚掷出的骰子**
- 主动玩家在自己回合结束时用的是 **bean field 中全部 5 颗骰子**

### 推荐实现解释

因此，收获后的“立即检查新当前卡”建议按**当前上下文**处理：

- 如果该玩家是在**别人的某次掷骰窗口**里收获：
  - 只用那一轮的 `current_roll`
- 如果该玩家是在**自己回合结束结算**时收获：
  - 用自己的 `bean_field`

这是对官方文字最一致的实现方式。

## 8.6 豆币应公开

官方明确写到：所有玩家都可以随时知道每个人当前拥有多少豆币。  
因此电子版应把分数作为 **公开信息**。

## 8.7 数字分数与实体牌堆的关系

虽然电子版可以把豆币显示成整数，但仍要注意：

- 额外的 1 或 2 枚豆币，在实体规则里确实是从牌堆里抽出来的
- 也就是说，**牌堆会因为得分而变薄**

因此逻辑层建议同时维护：

- `score: number`
- `draw_deck: HarvestCard[]`

不要因为 UI 只显示整数，就忽略牌堆消耗。

## 9. 终局

## 9.1 触发条件

如果任意玩家在一次收获后拥有 **10 或更多豆币**，则进入最终结算阶段。

注意：

- 商品页的简介把它简化成“达到 10 分就赢”
- 但完整规则不是立即停表，而是要做一次 **最终收尾**

## 9.2 若触发者不是当前主动玩家

如果达到 10 分的人不是当前回合的主动玩家，则：

1. 当前主动玩家必须 **立刻停止继续掷骰**
2. 将所有尚未放进豆田的骰子一并放入豆田
3. 用完整豆田再做 **最后一次自己的当前卡检查**
4. 然后进入全体最后收获

## 9.3 全体最后收获

之后，所有当前卡上已经完成了至少 3 条订单的玩家都可以收获。

电子版建议：

- 在最终结算阶段，持续循环允许玩家连锁收获
- 直到没有任何玩家还想或还能收获为止

## 9.4 胜负判定

- 豆币最多者获胜
- 并列则 **共同获胜**

## 10. 电子版最重要的状态机

## 10.1 建议的公共状态

```ts
interface PlayerState {
  id: string;
  score: number;
  topCard: HarvestCard;
  bottomCard: HarvestCard | null;
  coveredCount: 0 | 1 | 2 | 3 | 4 | 5;
}

interface TurnState {
  activePlayerId: string;
  beanField: Bean[];      // 已锁定骰子
  currentRoll: Bean[];    // 当前刚掷出的未锁定骰子
  rerollUsed: boolean;
  finalPhase: boolean;
}

interface GameState {
  players: PlayerState[];
  drawDeck: HarvestCard[];
  activePlayerIndex: number;
  beanPieceOwnerId: string;
  turn: TurnState;
}
```

## 10.2 建议事件

- `START_GAME`
- `START_TURN`
- `ROLL_FREE_DICE`
- `AUTO_RESOLVE_NON_ACTIVE_PROGRESS`
- `USE_REPEAT_ROLL`
- `LOCK_DICE_TO_FIELD`
- `CHECK_ACTIVE_CARD`
- `HARVEST`
- `TRIGGER_FINAL_PHASE`
- `FINAL_HARVEST_LOOP`
- `PASS_BEAN_PIECE`
- `END_GAME`

## 10.3 自动与手动的分界

### 应自动结算

- 每次 `current_roll` 产生后，所有非主动玩家是否能推进订单
- 主动玩家回合结束时，自己当前卡能推进多少条
- 收获后，新当前卡在“当前上下文”下能立即推进多少条

### 必须由玩家选择

- 主动玩家每次锁定哪几颗骰子
- 主动玩家是否使用整批重掷
- 任何玩家在满足 3 条订单后，是否立刻收获

## 11. 实现时容易写错的规则点

1. **主动玩家不能在中途就结算自己的当前卡。**
   只有所有 5 颗骰子都进入豆田后，才能一次性检查自己的卡。

2. **非主动玩家不能用豆田里的旧骰子。**
   他们只能用“刚刚掷出的那一批”。

3. **不同订单之间不消耗骰子，但同一订单内部每个需求位要占用独立骰子。**

4. **订单必须从下往上连续推进。**
   不能跳过一条未完成的底部订单去完成更上面的订单。

5. **收获是可选动作，不是强制动作。**
   玩家达到 3 条已完成后，可以先不收，等 4 条或 5 条再收。

6. **别人的回合里也能收获。**
   这要求服务端支持回合外中断动作。

7. **主动玩家的重掷会让别人再检查一次。**

8. **10 分不是立刻结束一切。**
   还要执行最终收尾与最后收获。

## 12. 规则歧义与推荐处理

以下两点官方文本没有写到足够细，电子版需要自行定规：

### 12.1 多名非主动玩家在同一掷骰窗口里都想收获，且其中一人因此触发终局

官方只说明“有人在收获后达到 10 分就进入最终阶段”，没有规定：

- 同一窗口里多个可选收获的精确优先级
- 是否先让所有声明收获的人都完成，还是一旦有人到 10 分就立即截断

推荐实现：

- 按座位顺序依次询问是否收获
- 一旦有人触发终局，立刻停止当前窗口的进一步自选收获
- 其余玩家仍可在“最终收获阶段”继续收获

这样规则简单、可复现，而且通常不会显著改变结果。

### 12.2 牌堆耗尽时的处理

官方只写了：

- 如果收获卡不够了，可以把一张概览卡翻到豆币面，拿来兑换 5 枚单独豆币

但没有明确写出：

- 被兑换出去的 5 张豆币牌是否重新进入某个可抽取区域
- 抽牌堆彻底为空且还需要新覆盖卡时该怎么做

推荐实现：

- 逻辑上仍保留有限抽牌堆
- 如果你想严格复刻实体玩法，这里需要额外 house rule 或实体确认
- 如果你只是要做可玩的电子版，最稳妥的办法是：
  - 分数显示为数字
  - 牌堆继续作为有限资源
  - 一旦牌堆空，阻止进一步需要抽牌的动作，并在设计层补一条明确规则
