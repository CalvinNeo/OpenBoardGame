# Task 191：回忆三重奏（Trio）

## 1. 游戏概述

- **中文名**：《回忆三重奏》 ｜ **英文名**：Trio（原名 nana） ｜ **线上版 game_id**：trio
- **设计**：宮野華也（Kaya Miyano） ｜ **发行**：Cocktail Games，2023 ｜ **美工**：Laura Michaud
- **人数**：3–6 人 ｜ **时长**：约 15 分钟 ｜ **适龄**：7 岁以上 ｜ **机制**：记忆 + 推理 + 成套收集
- turn_mode = "turn"（顺时针轮流行动，一个回合内可连续翻 3 张牌）
- 语言依赖：**零**。全数字，无文字、无发言。

36 张牌 = 数字 1–12 各 3 张。开局按人数发手牌，剩余的牌全部面朝下摊在桌子中央。
每个人的手牌必须**从小到大排序**，这是全部玩法的支点：轮到你时，你只能
「翻桌面暗牌」或者「要求任意一位玩家（含自己）亮出他手上**最小**或**最大**的那张」。
一个回合最多翻 3 张，只要翻出的数字和本回合已翻出的数字不一致，回合立刻结束，
所有翻开的牌全部复原（桌面牌盖回去，手牌回到原位）；三张全中就把这个数字收成一套「三重奏」。
率先收齐 3 套三重奏，或者收走 3 张 7（7 是最中间的数字，开局最难拿），立刻获胜。

## 3. 组件

### 3.1 数字牌

- 卡 id 形如 `n7-2`（数字 7 的第 2 张），全局唯一，序列化后仍可校验张数。
- 每张牌只有两个字段：数字（1–12）与副本序号（0–2）。**花色/颜色不进状态**，
  线上版改用「按数字着色」的方式上色（见 §6.3）。

### 3.2 桌面暗牌

- `state["table"]` 是一个**定长**列表，长度 = 9/8/6/6（3/4/5/6 人），
  位置固定，下标就是玩家记忆的坐标。已被收走的格子存 `None`。
- 桌面牌**没有**最小/最大限制，可以翻任意一张。

### 3.3 手牌

- `state["players"][pid]["hand"]` 是一个按数字升序的列表。
- 亮牌只能取 `hand[0]`（最小）或 `hand[-1]`（最大），且**可以要求自己**。
- 亮出的牌立刻离开手牌（实体规则是「面朝上放到他面前」），
  所以同一回合内连续要求同一个人，会依次拿到新的最小/最大牌。

## 4. 回合流程（服务端状态机）

```
stage = play      当前玩家连续执行 reveal，最多 3 次
stage = reveal    收成三重奏后的结算暂停，所有人按 Continue
stage = game_over 分出胜负，展示全部暗牌
```

一次 `reveal` 行动：

1. 取牌：`source="table"` 时取 `table[index]`；`source="hand"` 时取目标玩家 `hand` 的某一端。
2. 若本回合尚未翻牌 → 记为第 1 张，回合继续。
3. 若已翻 1–2 张且数字相同 → 记为下一张；若这是第 3 张 → **成功**，收走三张，进入 `reveal` 暂停。
4. 数字不同 → **失败**，本回合所有牌复原（桌面牌盖回、手牌回到原位），轮到下一位玩家。

复原的实现方式：翻牌时把牌从原容器里取出并记进 `state["revealed"]`（含来源、玩家、端、桌面下标），
失败时按记录逐张放回，因此「回到原位置和原状态」是精确的，不需要排序重算。

### 4.1 无人可翻的保护

极端情况下（桌面暗牌被收光且所有手牌为空）当前玩家可能没有任何合法行动。
`_start_turn` 会跳过这种玩家并写日志，避免死锁。实际对局中胜负条件远早于此触发。

### 4.2 死局判定（线上版补充规则）

理论上存在这样的局面：每个数字的三张牌都压在别人手牌中间，
没有任何玩家能在三次翻牌之内凑出同一数字的三张，此时谁都永远无法收牌。

线上版用「沉默回合」计数兜底：一次回合结束后，如果既没有收成三重奏，
也没有翻出任何**本局从未出现过**的新牌，`quiet_turns` 加一，否则清零。
当 `quiet_turns` 达到 `3 × 人数`（即连续三整轮所有人都只在翻旧牌）时，
判定平局，公开全部牌并结束本局。

这条规则不会影响正常对局：只要还有人能翻出新牌，计数就会被清零。
在 320 局机器人自对局中没有出现过平局，说明触发它确实需要极端牌序。

## 5. 胜负

- `mode = "simple"`（默认）：集齐 **3 套**任意三重奏，或集齐 **7 的三重奏**（即时）。
- `mode = "spicy"`：集齐 **2 套相连**的三重奏，或集齐 **7 的三重奏**。
  相连定义：`abs(a - b) == 7` 或 `a + b == 7`。1↔6、1↔8、2↔5、2↔9、3↔4、3↔10、4↔11、5↔12。
- 判定在每次成功收牌后立刻执行；达成即 `game_over`，胜者唯一。

## 6. 线上版设计决策

### 6.1 起始玩家

实体规则是「最近吃过牛油果的人先手」。线上版按座位顺序从 1 号座位开始，
并在 Help 的「开局」章节写明这一点。

### 6.2 再来一局的确认人数

重开一局沿用「所有人按下 Play again」的暂停模式，但**只统计真人座位**。
原因是服务器只在房间处于 `in_game` 时驱动机器人（`app.py` 的 `_maybe_run_bots`），
牌局结束后机器人不会被调用，如果把机器人也算进确认人数，重开就会永久卡住。

### 6.3 回合结算

DEV_GUIDE 要求「每轮结束后暂停，所有人点 Next Round 才继续」，本游戏**完全照做**，
而且失败回合同样结算——这正是玩家最需要看清楚的地方。

一个回合 = 一位玩家翻 1–3 张牌。无论收成三重奏还是翻错，回合都进入 `result` 阶段：

- **翻牌轨迹**：按顺序列出这一回合翻开的每一张牌，标出序号与来源
  （桌面 / 某人最小 / 某人最大）。
- **断点标记**：翻错的那一张标成红色 ✘，其余按 1、2、3 编号，
  一眼就能看出「第几张把链子打断了」。
- **一句话解释**：例如「第 1 张定下数字 8，第 3 张从桌面翻出 12，数字不同，
  回合就此结束，翻开的牌全部复原。」成功时则是「三张都是 8，收成一套三重奏(🌟)。」
- 所有人按 Continue 之后才轮到下一位玩家。机器人会自动按，
  所以只有真人需要点。

服务端把这些数据放在 `state["last_result"]`：`reveals` 是完整轨迹，
`failed_at` 是断掉的那一张的下标（成功时为 `None`）。
`get_public_view` 原样下发，因为这些都是全场都看见过的公开信息。

### 6.4 视觉与图标

- 桌面暗牌 🎴，手牌 ✋，三重奏 🌟，7 的三重奏 7️⃣，胜利 🏆，辣味模式 🌶️，简易模式 🍃。
- 数字牌按**数字**着色（1–12 映射到一圈色相），这样收成的三张牌天然同色，便于一眼确认。
  颜色是数字的冗余编码，不是额外信息，不存在泄露。
- 玩家自己的手牌全部明牌（你本来就看得见自己的手牌），别人的手牌只显示张数与背面。
  被翻开的手牌在结算前对所有人明牌。

### 6.5 确认蒙版的尺寸

单张暗牌在手机上只有 96×128（320px 宽时），手牌端点更是只有 21×29，
都放不下 Reveal / Cancel 两个按钮。按 DEV_GUIDE「蒙版一个足够大的上层容器」：

- **暗牌**：蒙版盖住整张牌桌（`#trioTable`），按钮放大到 46px 高。
  被选中的那张牌 `z-index` 抬到蒙版之上保持可见，
  按钮带则自动放到**不是选中牌所在行**的那一端（选中末行就放顶部，否则放底部），
  因此两者永远不会重叠。
- **手牌端点**：蒙版盖住整行玩家条，按钮 40px 高。
  端点瓦片前面还有姓名列，宽度随断点变化，所以蒙版的左右边界是
  **渲染后实测瓦片位置**算出来的，而不是写死偏移；窗口尺寸变化时重新测量。

### 6.6 手机端一屏布局

DEV_GUIDE 要求「布局尽量不要太长，导致需要上下滚动」「用满手机的一屏」
「减少大框套小框」。第一版把牌桌、翻牌条、玩家列表各套一层带底色的框，
在 320×640 上总高 832px，需要滚动 190px，而且三个框的 padding 与标题
白白吃掉 100 多像素。改法：

- **整块游戏区只保留一层深色底**：`.trio-root` 自带深色渐变底板。
  房间背景在多数主题下是浅色的，去掉区块底板后近白色文字会直接糊在浅底上，
  所以底色必须由游戏自己提供，而不是依赖房间主题。
- **区块全部拍平**：不再有 `.trio-block` 的边框、底色和 padding，
  只留一行小号大写标签。牌桌、翻牌条、玩家列表之间靠间距分组。
- **翻牌条并入牌桌**：标签、已翻的牌、提示文字挤在同一行，
  省掉一整行区块标题；结算时标签自动让位，说明文字独占一行。
- **牌桌让出纵向空间，按行数自适应**：桌面暗牌数量由人数决定（9/8/6/6），
  一律排成**最多两行**——不超过 6 张排一行，超过则两行。
  于是 6 人局桌面只有 55px 高，3 人局 139px，而不是原来的 244px。
- **牌桌限宽而不是拉满**：`width: calc(列数 × 卡宽 + 间距)`，
  必须给**确定宽度**而不是 `max-width`，因为 `1fr` 网格没有固有宽度，
  只给上限会让 flex 列在宽屏上塌掉。
- **玩家区接手让出来的空间**：每行从 34px 放大到 46px（390px 下 50px），
  手牌端点从 21×28 放大到 29×38，中间牌 21×28，名字 12px，
  三重奏筹码 18px 高。玩家区是真正要做决策的地方，值得这块地方。
- **状态条不重复**：轮次与「轮到谁」已经在状态条里，横幅只在
  结算、终局和翻牌进行中出现，正常回合不占那一行。
- **确认蒙版跟着变**：牌桌压到一两行后放不下按钮，蒙版改为向下生长，
  把按钮带停在牌桌下方（`bottom: -52px`），选中的牌仍然浮在蒙版之上，
  两者不会撞在一起。

### 6.7 隐藏信息纪律

- `get_public_view` 中：他人的手牌只给 `hand_count`；桌面暗牌只给 `face_up` 与 `number`（未翻开时为 null）。
- 只有 `game_over` 时才把全部手牌与桌面暗牌公开（与 BGA「All cards are now revealed at the end of the game」一致）。
- 机器人只能读到自己手牌 + 公开视图，绝不读 `state` 里的他人手牌或暗牌，
  它的推理完全基于「公开翻牌历史」重建（见 §8）。

## 7. 未实现的部分

- **团队模式**（4 人 / 6 人 2 人一队，共享三重奏 + 回合末换牌 / Pass）。
  该模式需要额外的换牌阶段与队伍计分，且 4 人局本就能开两队对战的替代玩法（两组人各记各的），
  线上版暂不实现，Help 中也不提及。

## 8. AI 设计

Trio 的机器人必须**靠记忆取胜**，因此本游戏在 `game/ai_metadata.py` 中登记为有专门策略，
Select Game 会显示 🤖。

### 8.1 记忆重建

`state["history"]` 记录每一次翻牌（来源、玩家、端、桌面下标、卡 id）以及该回合成败。
机器人不保存私有记忆，而是每次行动前**重放公开历史**，重建两类知识：

- `table_known[index] = card_id`：该桌面格子曾经翻开过，只要格子里的牌还是这张就仍然有效。
- `hand_known[pid][position] = card_id`：`position` 是这张牌在**初始升序手牌**中的下标。
  手牌只会从两端增删，牌不会换位，所以「某张牌在初始序列中的位置」是稳定坐标。
  配合 `lo_perm` / `hi_perm`（两端已被永久收走的张数）即可算出
  「现在要求某人亮最小牌会得到哪张」：`hand_known[pid][lo_perm]`。

重放时：一次成功回合的三张牌永久离场（对应端计数 +1）；失败回合的临时取出全部回滚。
机器人自己的手牌不需要记忆，直接按当前手牌与两端计数还原成完整的位置表，
因此它对自己的每一张牌都「知道在哪」。

### 8.2 行动选择

1. 把所有合法翻牌点列出来，每个点给一个**预测数字**：
   - 已知 → 确定的数字；
   - 未知 → 从「尚未定位的牌」中按均匀分布取候选，若该玩家手牌有已知邻居，
     再用升序约束把候选夹到 (`已知下界`, `已知上界`) 之间。
2. 必胜链搜索：把「当前可翻且已知会显示 N」的点列出来，做深度为剩余次数的 DFS。
   每一步都**重新计算**端点位置，因为连问两次同一端会往手牌里更深一层，
   所以「某人最小的两张是同一个数字」这种链也能被找到。
3. 若本回合已翻 1–2 张（目标数字 N）：选 P(数字 = N) 最大的点。
   全部为 0 时（这个数字已经凑不齐）改翻一个**没见过的点**，因为翻已知牌学不到任何东西。
4. 若本回合尚未翻牌：选「已知点数最多、且剩余同数字牌还没被定位的张数最多」的数字开局。
   注意这里偏好「未定位」而不是「已定位」——已定位却不在端点上的牌是永远翻不到的。

### 8.3 强度与自检

机器人不会偷看任何隐藏信息，强度来自「把公开信息全部记住」。测试里用 3–6 人、
简易与辣味两种模式跑机器人对局，断言对局能在有限步内终局且从未产生非法 action。
另外用 320 局自对局做过压力测试：全部终局、零平局、最长 155 步。
