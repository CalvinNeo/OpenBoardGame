# 游戏设计文档：印加宝藏 (Incan Gold / Diamant)

本文档旨在详尽描述《印加宝藏》的规则逻辑，以便于开发人员将其转化为电子游戏（代码实现）。

## 1. 游戏概述 (Overview)
* **类型**: 聚会游戏 / 运气 / 风险管理 (Push-your-luck)
* **玩家人数**: 3-8人 (电子版可支持 AI)
* **游戏结构**: 共进行 **5个回合 (Rounds)**
* **核心目标**: 在5个回合结束后，拥有最多的宝石（得分）即获胜。

---

## 2. 游戏组件与数据结构 (Components & Data Structures)

在电子版中，你需要初始化以下对象和变量。

### 2.1 卡牌库 (Deck Construction)
游戏总共有 **35张卡牌**，但在每一轮开始时，牌库的构成会有所不同。

1.  **宝藏卡 (Treasure Cards) - 共15张**
    * 数值定义: 定义一个数组包含以下数值：
        `[1, 2, 3, 4, 5, 5, 7, 7, 9, 11, 11, 13, 14, 15, 17]`
    * *功能*: 翻出时提供宝石。

2.  **灾难卡 (Hazard Cards) - 共15张**
    * 类型: 5种不同的灾难，每种3张。
    * 类型ID: `[Snake, Spider, Fire, Rockfall, Mummy]` (蛇, 蜘蛛, 火灾, 落石, 木乃伊)
    * *功能*: 同一种灾难在一轮中出现第二次时，回合强制结束。

3.  **神器卡 (Artifact Cards) - 共5张**
    * 数值: 随回合数增加而变化（或固定值，视版本而定，通常前3张为5分，后2张为10分，或者统一处理）。
    * *电子版推荐设定*:
        * Round 1-3 放入的神器: 价值 5
        * Round 4-5 放入的神器: 价值 10
    * *特殊规则*: 只有当玩家**独自一人**选择离开探险时，才能拿走路径上的神器。

### 2.2 玩家对象 (Player Object)
每个玩家实例应包含：
* `id`: 唯一标识符
* `banked_gems`: int (帐篷里的宝石，**安全积分**，不可通过游戏机制减少)
* `hand_gems`: int (手上的宝石，**风险积分**，回合结束未回家则归零)
* `status`: enum (`In_Cave` / `In_Camp`) (当前状态：探险中 / 已回家)

### 2.3 全局游戏状态 (Global State)
* `current_round`: int (1-5)
* `path_cards`: List (当前回合路径上已翻开的卡牌)
* `deck`: List (当前回合的抽牌堆)
* `gems_on_cards`: Map/Dictionary (存储路径上每张卡牌剩余的宝石数，即“余数”)

## 3. 游戏流程逻辑 (Game Loop)

以下逻辑伪代码描述了从游戏开始到结束的完整流程。

### 3.1 游戏初始化 (Game Setup)
1.  初始化所有玩家 `banked_gems = 0`, `hand_gems = 0`。
2.  初始化基础牌库 `Base_Deck` = 15张宝藏卡 + 15张灾难卡。
3.  初始化神器堆 `Artifacts` = 5张神器卡（按顺序标记）。
4.  `current_round = 1`。

### 3.2 回合开始 (Round Start)
1.  **构建牌库**:
    * 取出 `Base_Deck`。
    * 加入 1 张当前回合对应的神器卡。
    * 洗牌 (Shuffle)。
    * *注意*: 随着游戏进行，之前的回合可能会永久移除某张灾难卡，需确保构建牌库时该卡已不在 `Base_Deck` 中。
2.  重置玩家状态: 所有玩家 `status = In_Cave`, `hand_gems = 0`。
3.  清空路径: `path_cards = []`。

### 3.3 回合循环 (Turn Loop)
只要有玩家还在探险 (`In_Cave`) 且未发生“灾难爆发”，循环继续。

#### A. 翻牌阶段 (Reveal Phase)
1.  从 `deck` 顶端抽取一张卡 `new_card`。
2.  将 `new_card` 加入 `path_cards`。
3.  **判断卡牌类型**:

    * **情况 1: 宝藏卡 (Treasure)**
        * 获取宝藏数值 `val`。
        * 获取当前在洞穴中的玩家数 `active_player_count`。
        * 计算平分: `share = floor(val / active_player_count)` (向下取整)。
        * 计算余数: `remainder = val % active_player_count`。
        * **分配**:
            * 所有 `status == In_Cave` 的玩家: `hand_gems += share`。
            * 将 `remainder` 存储在该卡牌对象上 (作为路上的遗留宝石)。

    * **情况 2: 灾难卡 (Hazard)**
        * 检查 `path_cards` 中是否已经存在一张**相同类型** (`type`) 的灾难卡。
        * **如果不存在 (第一次出现)**:
            * 什么都不发生，作为警告。继续游戏。
        * **如果存在 (第二次出现 - 灾难爆发)**:
            * **回合立即失败**。
            * 所有 `status == In_Cave` 的玩家: `hand_gems = 0` (失去本轮所有手持宝石)。
            * **移除灾难逻辑**:
                * 将刚刚翻出的这张灾难卡从游戏中**永久移除** (Remove from game)。
                * *注意*: 路径上那张旧的同类灾难卡保留，洗回牌库用于下一轮。
            * 跳出“回合循环”，直接进入 **3.4 回合结算**。

    * **情况 3: 神器卡 (Artifact)**
        * 不发生立即分配。
        * 神器卡留在路径上，等待玩家“独自离开”时捡取。
        * *注意*: 前3张神器卡若被捡起值5分，后2张值10分。如果在路径上没被捡走，本身无价值。

#### B. 玩家决策阶段 (Decision Phase)
* 如果发生了“灾难爆发”，跳过此阶段。
* 询问所有 `status == In_Cave` 的玩家。
* **输入**: 每个玩家必须同时选择 `Continue` (继续探险) 或 `Leave` (回营地)。
    * *实现细节*: 电子版应设置倒计时，所有玩家选择完毕后统一揭示。

#### C. 决策结算阶段 (Resolution Phase)
1.  统计选择 `Leave` 的玩家列表 `leaving_players`。
2.  统计 `leaving_players` 的数量 `count`。

    * **如果 count > 0 (有人离开)**:
        * **平分路上的宝石**:
            * 遍历 `path_cards` 中所有有剩余宝石 (`remainder > 0`) 的宝藏卡。
            * 计算总剩余宝石 `total_remainders` (或者逐张卡计算，规则效果一样)。
            * *标准规则通常是逐张卡计算*: 对于每张卡上的 `remainder`:
                * `share = floor(remainder / count)`
                * `new_remainder = remainder % count`
                * 每个离开的玩家获得 `share`。
                * 卡上更新为 `new_remainder`。
        
        * **处理神器 (Artifacts)**:
            * **如果 count == 1 (只有一人离开)**:
                * 该玩家获得路径上**所有**的神器卡。
                * 将这些神器卡从 `path_cards` 移出，转化为该玩家的分数 (5或10)。
            * **如果 count > 1 (多人同时离开)**:
                * **没有人**能获得神器。
                * 路径上的神器卡**不被移出**，继续留在路径上？
                * *规则澄清*: 标准规则中，如果多人离开，神器**被移除游戏**（视为无人能以此换取分数），或者留在路径上等待下一批人？
                * *最通用的电子版规则*: 如果多人离开，神器被视为“由于争抢而导致无人获得”，**神器卡直接从游戏中移除 (Remove from Game)**，本局游戏不再出现。

        * **入库 (Banking)**:
            * 所有 `leaving_players` 执行:
                * `banked_gems += hand_gems`
                * `hand_gems = 0`
                * `status = In_Camp` (本轮不再参与)。

3.  检查是否所有玩家都已 `In_Camp`。如果是，本轮结束，进入 **3.4 回合结算**。
4.  否则，返回 **A. 翻牌阶段**。

### 3.4 回合结算 (End of Round)
1.  如果是“灾难爆发”导致的结束，移除那张触发的灾难卡。
2.  如果是所有玩家主动回家导致的结束，不需要移除任何卡。
3.  将路径上剩余的所有卡牌（宝藏、未触发的灾难、未被拿走的神器）洗回 `Base_Deck`。
    * *注意*: 已经“永久移除”的灾难卡和神器卡不洗回。
4.  `current_round += 1`。
5.  如果 `current_round > 5`，进入 **4. 游戏结束**。
6.  否则，开始下一轮。

---

## 4. 游戏结束与计分 (Game Over)
1.  显示计分板。
2.  排序依据: `banked_gems` (从高到低)。
3.  最高分者获胜。
4.  平局处理: 通常共享胜利，或者拥有最多神器卡数量者胜（可选规则）。

---

## 5. 特殊边界情况处理 (Edge Cases for Implementation)

1.  **最后一张卡**: 理论上牌库可能被抽空（极少见），若抽空则该轮直接结束。
2.  **整除逻辑**: 务必使用整数除法（向下取整）。例如 3个宝石 2人分，每人得1，剩1在卡上。
3.  **神器争夺**: 必须强调 `count == 1` 的判断。这是博弈的核心点。
4.  **UI展示**:
    * 必须清晰展示：当前手牌风险分 vs 已入库安全分。
    * 必须清晰展示：路径上每张卡堆积的“余数”宝石（这是诱惑玩家离开的关键）。
    * 必须清晰展示：已翻出的灾难卡（提示玩家下一张可能爆掉的概率）。

## 6. AI 行为逻辑参考 (Simple AI Logic)

如果你需要开发单人模式，AI 的基础逻辑可以是：
* **保守型 AI**: 当 `hand_gems` > 10 或 场上出现 2 种不同灾难时，选择离开。
* **贪婪型 AI**: 只有当场上出现 3 种不同灾难，或者 `hand_gems` > 20 时才离开。
* **计算型 AI (概率)**:
    * 计算牌库剩余卡牌总数 `remaining_cards`。
    * 计算会导致爆炸的灾难卡数量 `danger_cards` (即场上已有的灾难类型的剩余份数)。
    * 爆炸概率 `P(bust) = danger_cards / remaining_cards`。
    * 如果 `P(bust) > 阈值 (如 25%)`，选择离开。
    * *进阶*: 如果场上有大量余数宝石或神器，且判断其他玩家可能不走，适当降低风险阈值以尝试独吞。
